# L1 组件题

这一组题用来确认候选人能否把四组件心智模型（感知、规划、工具、记忆）变成能工作的 loop、schema 和停止条件。

## 题库

覆盖四类题型：概念、实现、调试、设计。

### 概念

#### 1. 解释 Agent 四个核心组件。

**答题要点：**

- 感知 把输入、工具、观察变成 context。
- 规划 决定下一步做什么。
- 工具 执行外部动作。
- 记忆 保存跨步骤或跨会话的上下文。

**面试官想听什么：**

- Trade-off：组件边界清晰让失败可定位，但真实系统会漏——糟糕的 tool result 常常看起来像记忆问题，反之亦然。
- 生产反例：一个预订 Agent "记得"取消过的订单，因为取消这个观察从未写进工作状态；问题出在感知到记忆的交接，而不是模型。
- 数据思维：在每个组件边界埋计数（看到的输入、发出的计划、调用的工具、记忆读写），才能说出哪个组件先劣化。

**加分项 / 常见错误：**

- 加分：说明每个组件各自会怎么挂，以及每个边界的最小日志点长什么样。
- 错误：只画组件图，不说失败如何在组件之间传播。

#### 2. 什么是 ReAct loop，它为什么有效？

**答题要点：**

- ReAct 交替进行 Reason（思考）和 Act（工具调用），Observation 喂给下一步。
- 它有效是因为中间步骤可检查，模型能根据观察自我纠正。
- loop 由停止条件约束：max steps、final answer、策略检查。

**面试官想听什么：**

- Trade-off：reasoning token 提升任务成功率，但每步增加延迟和成本；步数超过某一点后准确率不再增长。
- 生产反例：一个 Agent 在不稳定的 API 上陷入 think-act-observe 循环，重试烧掉的 token 比任务本身还值钱；加一个"降级数据继续"的分支更便宜。
- 数据思维：把任务成功率对步数画曲线；曲线平台期就是步数预算，而不是随便取个整数。

**加分项 / 常见错误：**

- 加分：指出 observation 必须真实；如果工具返回的是包装过的错误而不是真数据，loop 就是在垃圾上推理。
- 错误：把 ReAct 说成"就是工具调用"，忽略 observe-and-correct 循环。

#### 3. Agent 里 planning 和 execution 有什么区别？

**答题要点：**

- planning 在行动前选择顺序或策略；execution 执行步骤并可能修改计划。
- 好计划便宜、可错、可检查；execution 暴露计划看不见的现实。
- 好答案能区分单步工具选择与多步计划生成。

**面试官想听什么：**

- Trade-off：先规划让长任务更连贯，但费 token，且第一个工具结果就可能推翻计划；边做边计划用连贯性换响应速度。
- 生产反例：旅行 Agent 生成详细行程，第一个航班 API 返回无结果，计划作废；基于观察重新规划胜过原始计划。
- 数据思维：统计计划有效性（实际执行路径与计划吻合的比例）和重新规划率；40% 的重规划率说明计划只是装饰。

**加分项 / 常见错误：**

- 加分：把计划当便宜假设，execution 可以随时修订。
- 错误：模型写得自信就认为计划是对的。

### 实现

#### 4. 如何设计一个 LLM 能稳定使用的工具 schema？

**答题要点：**

- 一个工具只做一件事；名字和描述说明"何时用"，而不只是"它做什么"。
- 输入输出类型化并校验；描述是写给模型的，不只是给人类看的。
- 错误与空结果可区分；schema 里包含明确的"没查到数据"状态。

**面试官想听什么：**

- Trade-off：更丰富的描述提升工具选择准确率，但每一步都耗 token；短名字加好描述胜过长名字加模糊描述。
- 生产反例：`search_documents` 和 `search_documents_v2` 两个工具让模型选了废弃版本；加版本别名和弃用说明就修好了，无需重训。
- 数据思维：记录工具选错后被纠正的混淆案例，用这些数据调描述，而不是凭直觉。

**加分项 / 常见错误：**

- 加分：对输出做 schema 校验，返回结构化错误码，让 loop 能程序化响应。
- 错误：把失败藏在 200 响应中的错误字符串里，Agent 分不清失败和空成功。

#### 5. 短期记忆和长期记忆各放什么？

**答题要点：**

- 短期记忆存当前对话和任务状态。
- 长期记忆存持久事实、偏好或策略。
- 长期记忆必须做作用域限定、过期检查、隐私敏感处理。

**面试官想听什么：**

- Trade-off：长期记忆带来个性化并省 token，但陈旧或错误的事实会毒化答案；短期记忆诚实但会忘。
- 生产反例：支持 Agent 用了存了一年多的"偏好语言"回答，答错了语言；修复是给每条记忆加时间戳，读取时做新鲜度检查。
- 数据思维：把 retrieval 证据和用户 profile 分开；在纠正样本上先测 profile 命中准确率，再规模化信任记忆。

**加分项 / 常见错误：**

- 加分：把记忆写入设计成显式、可审查的事件，而不是静默后台保存。
- 错误：因为"以后可能有用"就存敏感数据，没有保留策略。

#### 6. 为什么 ReAct loop 要设 max step limit？

**答题要点：**

- 防止无限循环，限制延迟与成本。
- 强制进入终态，让失败可见、可调试。
- 触发时要有个策略决定：fail、clarify、summarize 还是 escalate。

**面试官想听什么：**

- Trade-off：限额太低砍掉合法长任务；太高让失控循环一直烧到账单。
- 生产反例：监控任务里 50 步上限的 Agent 对着不稳定状态接口循环了一整晚；按工具加重试上限加总预算才止血。
- 数据思维：统计成功任务所需步数分布，用 95 分位加余量当上限，而不是拍脑袋。

**加分项 / 常见错误：**

- 加分：同时用步数预算和 token 预算，因为一大步可能比十小步还贵。
- 错误：把步数上限当安全网，却不管每步成本。

#### 7. 如何正确地让 Agent loop 停下来？

**答题要点：**

- 定义显式停止条件：产出 final answer、达到 max steps、违反工具策略、安全检查触发。
- 区分"完成了"和"放弃了"：两者都要对调用方可见。
- 停止逻辑放在模型之外，模型无法说服它继续。

**面试官想听什么：**

- Trade-off：模型自己决定停止灵活但不可靠；代码强制停止可靠，但每条路径都要显式规则。
- 生产反例：prompt 写"不确定就继续问澄清问题"且没有预算，Agent 无限循环；加硬轮次上限和澄清预算修好。
- 数据思维：按会话记录停止原因，prompt 改动后监控停止原因分布是否偏移。

**加分项 / 常见错误：**

- 加分：输出结构化终态（completed、max_steps、aborted、safety_blocked）供下游处理。
- 错误：指望模型"自觉"停下来，没有任何外部预算。

### 调试

#### 8. Agent 调错了工具，如何调试工具选择？

**答题要点：**

- 用完全相同的 prompt、context 和工具列表复现。
- 先查工具描述与名字歧义，再查 schema 和示例。
- 看错误调用后模型收到的 observation；选择可能没错，是反馈误导。

**面试官想听什么：**

- Trade-off：工具越多能力越强，但选择准确率下降；每加一个工具都要写有区分度的描述。
- 生产反例：加了第 12 个描述重叠的工具后，选择准确率掉了 8 个点；合并两个工具并写决策表恢复。
- 数据思维：维护"意图 vs 实际选择"的混淆矩阵，优先修混淆最高的几对。

**加分项 / 常见错误：**

- 加分：在描述里加"何时不要用本工具"小节。
- 错误：没检查描述是否有区分度就先怪模型。

#### 9. 工具返回了有效数据，但 Agent 答错了，如何调试？

**答题要点：**

- 确认 observation 是否完整、未解析错误地进入 context。
- 检查单位换算、时区、工具输出与答案之间的字段映射。
- 用相同 context 重放该步骤，区分模型错误与数据错误。

**面试官想听什么：**

- Trade-off：严格解析防止静默损坏，但遇到新字段形状会挂；宽容解析更稳，但可能映射错字段。
- 生产反例：天气 Agent 报了错误城市的温度，因为 API 响应里 "name" 的语义和模型假设不同；修法是 schema 里显式字段映射。
- 数据思维：对比原始工具输出与模型引用内容的一致性；持续不为零的不一致率说明是 schema 或解析 bug，不是幻觉。

**加分项 / 常见错误：**

- 加分：trace 里保留原始 tool payload，字段映射 bug 才有据可查。
- 错误：没查数据路径就把所有错答归为幻觉。

### 设计

#### 10. 为一个跨会话的支持 Agent 设计记忆与 context 管理。

**答题要点：**

- 定义存什么（事实、偏好、已解决状态）、什么过期、什么绝不存。
- 短期任务状态按会话存，长期 profile 事实单独存。
- 每次记忆读取都带来源和新鲜度检查；敏感写入需要显式同意。

**面试官想听什么：**

- Trade-off：记忆越多个性化越好，但陈旧、隐私和检索噪声风险越高。
- 生产反例：健康助手存了一次筛查日期后从不作废，后来用过期信息回答资格问题；加 TTL 策略字段和重新验证触发器修好。
- 数据思维：测量记忆读写比和检索事实命中率；命中率低说明问题在 retrieval，不在存储。

**加分项 / 常见错误：**

- 加分：提供忘记/纠正路径，让用户能删除错误记忆。
- 错误：为了"将来有用"存一切，没有保留策略也没有删除 API。

#### 11. 为可以写入外部系统的 Agent 设计 guardrail。

**答题要点：**

- 执行前按可逆性、爆炸半径、数据敏感度对动作分类。
- 破坏性写入需要确认或审批；只读动作可自动化但要限流。
- 策略用代码强制、写审计日志、执行后验证结果。

**面试官想听什么：**

- Trade-off：代码强制的 guardrail 可靠但僵化；模型层判断灵活但不可靠，安全关键检查必须放代码。
- 生产反例："发邮件前确认"的提示被绕过——模型把邮件总结成"最终确认预览"，用户随手点过；修法是模型无法措辞的独立确认步骤。
- 数据思维：跟踪 guardrail 触发率和覆盖率；覆盖率高说明 guardrail 要么错了，要么用户根本看不见。

**加分项 / 常见错误：**

- 加分：guardrail 是外圈，prompt 是内圈；绝不让 prompt 成为唯一屏障。
- 错误：相信强大的 system prompt 足以保护不可逆操作。

## 追问池

- 工具反馈模糊时会坏在哪里？
- 达到 step limit 应该 fail、clarify、summarize 还是 escalate？
- 如何避免把敏感数据存进记忆？
- 如何阻止 Agent 在只有过期检索上下文时用工具？
- 生产里好的停止条件日志长什么样？

## 常见红旗

- 把 max steps 当固定常量，而不是测量出来的预算。
- 分不清模型错误与工具数据错误。
- 把记忆当只追加存储，没有新鲜度、没有同意。
- 没有任何代码强制控制，就信任模型会自己停止或保持安全。
- 把 ReAct 说成工具调用，忽略 observe-and-correct 循环。

## 作品集证据

L1 可接受的证据：

- 一个带实测步数预算和停止原因的可运行 ReAct loop。
- 一个有类型化输入、输出校验、可区分空结果的工具 schema。
- 一个区分短期状态与长期 profile 事实的记忆设计。
