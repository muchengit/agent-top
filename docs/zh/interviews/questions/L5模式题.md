# L5 模式题

这些问题考察候选人能否定义标准并产生外部影响力：原创模式、架构权衡、开源贡献和垂直专家证据。覆盖概念、实现、调试、设计四类题型。

## 题库

### 概念

#### 1. 什么让可复用 Agent 模式有价值？

**答题要点：**

- 它解决跨上下文的重复问题，而不是一次性任务。
- 它有稳定输入输出和显式失败模式。
- 它把安全与验证作为一等公民。
- 它比框架特定代码更容易维护。
- 它带评估集，证明何时有用、何时无用。

**面试官想听什么：**

- Trade-off：太抽象的模式不可证伪；太具体则不可复用。价值在于你划的边界和你附上的证据。
- 生产反例：名为"记忆模式"实为数据库包装，没有解决新鲜度和隐私，只是增加仪式；有价值的版本定义了记忆何时写入、读取、遗忘。
- 数据思维：模式应自带成功指标——在多少个点上、提升了多少准确率、延迟或成本。

**加分项 / 常见错误：**

- 加分项：说明模式何时该变成框架（当同样的边界在多处都需要时）。
- 常见错误：把库称为"模式"，却不定义它抽象的问题。

#### 2. 如何评估自研框架还是使用现有框架？

**答题要点：**

- 只有现有框架隐藏了重复问题或让失败模式不清晰时才自研。
- 当现有框架覆盖状态、工具、可观测性和生态需求时使用它。
- 框架代码隔离并锚定版本（`tested_against`）。
- 投入前先测试采用成本和维护成本。

**面试官想听什么：**

- Trade-off：框架买"电池"但失去控制；手写代码透明但每个功能都要付费。
- 生产反例：团队自研的"轻量框架"只是现有 SDK 加一层配置；抽象隐藏了版本漂移，花费超过了节省。
- 数据思维：在同一任务上度量两条路径的交付时间和调试时间再决定。

**加分项 / 常见错误：**

- 加分项：定义退出条件——当抽象比其包裹的框架更贵时。
- 常见错误：框架部落主义，按品牌选而不是按失败模式。

### 实现

#### 3. 如何为重复问题设计原创模式？

**答题要点：**

- 从你见过两次以上的具体失败开始。
- 提取不变量：必须始终为真的东西（接地、幂等、权限检查）。
- 定义边界：输入、输出，以及模式拒绝做什么。
- 以最简形式实现，然后在黄金集上评估。
- 记录权衡和要避免的反模式。

**面试官想听什么：**

- Trade-off：原创模式应不止是改名；它必须改变可测量的结果。
- 生产反例：只是 prompt 指令的"验证门禁"模式毫无价值，直到它变成带自己评估集的代码门禁。
- 数据思维：用模式自己的评估展示准确率、延迟或成本的前后对比。

**加分项 / 常见错误：**

- 加分项：用案例研究和开源证据发布模式。
- 常见错误：为标准实践发明术语并称其为原创。

#### 4. 如何防止框架变更毁掉文档和评估？

**答题要点：**

- 把框架特定代码隔离在 Labs 和示例中，而不是概念文档里。
- 每个框架示例锚定 `tested_against` 和 `validated_date`。
- 原理文字保持独立于框架 API。
- 每次框架升级重跑评估集；把版本变更当作发布事件。
- 框架弃用时，先标记文档 deprecated 并链接替代品，再归档。

**面试官想听什么：**

- Trade-off：版本固定保护可复现性但延迟采用；CI 检查自动检测滞后以平衡两者。
- 生产反例：引用已改名 SDK 函数的教程静默腐烂了两个季度；加上版本锚后 CI 新鲜度检查才捕获。
- 数据思维：把文档版本到 SDK 版本的滞后作为指标追踪；超过阈值就告警。

**加分项 / 常见错误：**

- 加分项：定期任务探测框架示例并开 sync-required issue。
- 常见错误：每次框架变化就重写原理文档——那是折腾，不是维护。

### 调试

#### 5. 调试生产中的模式失败："先验证后行动"门禁被绕过。

**答题要点：**

- 回放 trace：找出哪条代码路径跳过了门禁以及为什么。
- 检查门禁是代码强制还是 prompt 建议。
- 查找共享相同处理器的路径：预览、确认和执行可能共享削弱边界的代码。
- 通过结构化修复：分离处理器、分离权限、显式状态机。
- 添加回归测试尝试每一种绕过路径。

**面试官想听什么：**

- Trade-off：结构化门禁更安全但代码更多；prompt 门禁便宜但只是建议。失败模式决定你需要哪种。
- 生产反例：门禁在测试中通过，因为测试调用的是 happy-path 处理器；绕过发生在共享同一权限检查的另一个处理器。
- 数据思维：追踪门禁命中率与绕过尝试率；成功的绕过尝试是 P0。

**加分项 / 常见错误：**

- 加分项：用每种状态转移模糊测试门禁，证明它无法被跳过。
- 常见错误：打 prompt 补丁就宣布模式修复。

#### 6. 如何用证据证明垂直专家能力（金融、医疗等）？

**答题要点：**

- 构建领域评估集：监管用例、边界用例和该垂直领域特有的拒绝用例。
- 展示测量结果：该集上的准确率、误拒绝率和误接受率。
- 文档化领域约束：合规、审计、数据驻留和可解释性要求。
- 发布可迁移到其他团队的模式或案例研究。
- 获得外部验证：PR、演讲、论文或采用。

**面试官想听什么：**

- Trade-off：垂直专家能力花费时间和数据访问；证据把声明与已证明的能力分开。
- 生产反例：简历写"医疗 AI"却没有一个监管边界用例或评估结果；证据是评估集和事故历史。
- 数据思维：展示数字——多少个领域用例、什么通过率、误拒绝成本多少、什么审计结果。

**加分项 / 常见错误：**

- 加分项：公开工件（博客、论文、开源 lab）让别人可验证。
- 常见错误：罗列领域关键词却无可测量结果。

### 设计

#### 7. 设计防止 Agent 工具调用双重执行的模式。

**答题要点：**

- 每个变更类工具调用要求幂等键。
- 键从请求上下文派生（用户、动作、实体、去重窗口）。
- 存储已执行键并带 TTL；重试时返回原始结果而不是重新执行。
- 添加执行后验证步骤，确认副作用恰好发生一次。
- 用重试风暴和并发调用测试。

**面试官想听什么：**

- Trade-off：幂等付出存储和键设计成本，但消除 Agent 系统最严重的失败类（双重副作用）。
- 生产反例：支付相关调用超时，Agent 重试，因为工具不幂等，动作执行了两次。
- 数据思维：度量超时-成功比——调用失败但副作用已发生的比例——决定何时重试安全。

**加分项 / 常见错误：**

- 加分项：要求每个有状态的 MCP 工具接受幂等键。
- 常见错误：假设超时意味着动作没有发生。

#### 8. 设计模式变成框架或标准的决策框架。

**答题要点：**

- 统计独立采用者和上下文的数量。
- 度量作为重复代码的模式维护成本。
- 定义契约：schema、语义、失败模式和版本化。
- 决定治理：谁审查变更、版本如何发布、弃用如何运作。
- 标准要带测试和示例发布，而不只是文档。

**面试官想听什么：**

- Trade-off：过早标准化锁定错误；过晚标准化放大迁移成本。触发点是重复的、相同边界的证据。
- 生产反例：两个团队三次写出相同的工具边界代码，之后才有共享的 MCP 风格标准；第三个团队付了前两个的学费。
- 数据思维：追踪重复指标——同一模式有多少份拷贝——来论证标准化。

**加分项 / 常见错误：**

- 加分项：让标准成为活的工件，带版本化示例和迁移指南。
- 常见错误：写没有实现、测试或弃用路径的标准。

## 追问池

- 模式何时该变成框架？
- 如何证明模式不只是改名？
- 手写框架的退出条件是什么？
- 框架弃用时如何迁移文档？
- 你会先标准化哪个依赖，为什么？

## 常见红旗

- 没有评估证据的模式声明。
- 框架部落主义而非度量失败模式。
- 框架特定代码混进原理文档。
- 没有版本锚或新鲜度检查。
- 没有实现、测试或弃用路径的标准。

## 作品集证据

L5 可接受的证据是：

- 带案例研究、评估集和前后指标的原创模式。
- 别人可验证的开源 PR、论文或演讲。
- 展示监管和边界用例覆盖的垂直领域评估报告。
- 带版本化和迁移指南的标准或框架贡献。
