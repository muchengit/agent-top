# L0 入门题

这一组题用于确认候选人在进入 Agent loop、工具调用或框架选择之前，是否已经掌握基础概念。

## 题库

覆盖四类题型：概念、实现、调试、设计。

### 概念

#### 1. prompt 和 system instruction 有什么区别？

**答题要点：**

- prompt 是用户可见的请求或任务；system instruction 设定角色、约束、输出格式和安全边界。
- system instruction 通常在多轮中保持稳定；prompt 随用户和任务变化。
- 好答案会说出一个混用后的失败模式，例如约束泄露或安全边界变弱。

**面试官想听什么：**

- Trade-off：保持 system 行为固定更容易调试，但也更僵化；允许 prompt 覆盖 system 规则更灵活，代价是安全。
- 生产反例：把客户请求原样拼进 system 位置，等于让用户可控文本覆盖你的策略——无意的 prompt injection。
- 数据思维：改 system prompt 后统计格式违规率；措辞一改格式失败率就跳 2 个百分点，这是信号不是噪声。

**加分项 / 常见错误：**

- 加分：提出把不变规则（system）与任务指令（user）分离，并分别测试。
- 错误：声称 system instruction 比 prompt "更重要"；它们是信任度和更新节奏都不同的两层。

#### 2. 为什么 context window 大小很重要？

**答题要点：**

- context 是 instructions、history、tool results、output 的有限预算。
- 更大的 context 不会自动解决 latency、cost、噪声问题，只是移动了权衡点。
- overflow 表现为裁剪、摘要，或模型对关键部分的注意力下降。

**面试官想听什么：**

- Trade-off：更大的窗口减少截断，但每轮成本更高，且注意力常被稀释，所以 retrieval 和 trimming 仍然必要。
- 生产反例：200k token 窗口里塞进 180k 陈旧日志，答案反而不如裁剪到 4k、只留相关行的 prompt。
- 数据思维：统计每轮实际 context 使用率；如果中位数请求填满 90% 窗口，问题在 retrieval，不在窗口大小。

**加分项 / 常见错误：**

- 加分：提到 "lost in the middle" 退化现象，把关键证据放在 context 的开头或结尾附近。
- 错误：把 context window 当免费内存，"反正装得下"就全塞进去。

#### 3. 用大白话解释 tokenization。

**答题要点：**

- 文本被切成模型 token，而不是天然按词切；标点、代码、多语言文本切法不均。
- token 决定 cost、latency 和长度上限；字符数不等于 token 数。
- 先粗略预算再谈精确计算：用"约 4 个字符 ≈ 1 个 token"当心算模型，然后用真实 tokenizer 验证。

**面试官想听什么：**

- Trade-off：不同语言 tokenizer 效率不同；"I" 是一个 token，而一个 CJK 字符可能是一个或多个，跨语言成本比例会变。
- 生产反例：中英混排的 prompt 比同内容单语言贵一截；emoji 多的字符串可能烧掉几十个 token。
- 数据思维：把 token 数和请求元数据一起打日志，成本回归按功能可见，而不是只看账单总额。

**加分项 / 常见错误：**

- 加分：提到 retry 会成倍放大 token 成本，token 密集的流程里 5% 失败率是一条可量化的预算线。
- 错误：把某个固定字符/token 比例当成放之四海皆准的公式。

#### 4. 什么样的 Agent system prompt 才算好？

**答题要点：**

- 清楚的任务边界、输出格式或停止条件、工具使用策略、安全与升级规则。
- 包含 refusal 或 escalation 行为，以及 example 或 output contract。
- 避免隐式假设和过长的指令。

**面试官想听什么：**

- Trade-off：指令更多减少歧义，但占用 context 且可能过度约束模型；每条规则都应"挣回"它的 token。
- 生产反例：3000 token、介绍整个公司的 system prompt，工具选择准确率反而不如 300 token、带一张"何时调用哪个工具"表格的 prompt。
- 数据思维：把 system prompt 当假设；上线前在 held-out eval 集上对 prompt 变体做 A/B。

**加分项 / 常见错误：**

- 加分：给 system prompt 做版本，并绑定 eval 分数，让每次改动可审计。
- 错误：写超长 prompt "以防万一"，却不测量每条规则是否真的改变行为。

#### 5. model output 和 final user response 有什么区别？

**答题要点：**

- raw model output 可能被 post-processing 改写：validation、formatting、redaction、citation enrichment。
- 推理文本必须和最终答案分离；tool output 可能被 summarize 或 normalize。
- 调试时 trace 应同时保留 raw 和 final answer。

**面试官想听什么：**

- Trade-off：post-processing 提升安全与一致性，但增加延迟，还可能把模型漂移藏进管线里。
- 生产反例：一个 citation 过滤器悄悄丢掉唯一正确的来源，一周后才有人在 diff raw 与 final 输出时发现 bug。
- 数据思维：按比例抽样部分轮次，统计"final 与 raw 不一致"的转化率，提前发现漂移。

**加分项 / 常见错误：**

- 加分：打一个稳定 correlation ID，把 raw output、final response、tool results 串成一条 trace。
- 错误：把 model output 和用户看到的 response 当成同一个东西，导致调试错了层。

### 实现

#### 6. 如何 debug 一个糟糕的 LLM response？

**答题要点：**

- 动手之前先区分 prompt、context、model、tool result、parsing 这几层。
- 从 logs、trace、sample input、expected output 入手，构造最小可复现案例。
- 不要一上来就说"换模型"。

**面试官想听什么：**

- Trade-off：全量 trace 诊断最快但费存储；采样 trace 在成本与可调试性之间平衡。
- 生产反例：一个"幻觉"答案其实是过期的缓存 tool result 被并进 context，模型本身没问题。
- 数据思维：按层给一周的失败样本分类；如果 70% 是 parsing 错误，换模型毫无帮助。

**加分项 / 常见错误：**

- 加分：用相同 context、相同模型和 temperature 重放，隔离非确定性。
- 错误：不保存失败输入就改 prompt，修复无法验证也无法回归测试。

#### 7. 什么时候 Agent 应该直接回答，而不是调用工具？

**答题要点：**

- 判断请求是否需要 live data、外部动作或权限；稳定事实和澄清可以直接回答。
- 当前事实、权限、写入才走 tool call；需要确定性或安全审查时升级。
- 默认值由歧义和风险决定，而不是由功能名称决定。

**面试官想听什么：**

- Trade-off：直接回答便宜快速但会过期；工具调用更正确但增加延迟、成本和失败面。
- 生产反例：内部 FAQ 机器人为了省一次工具调用，凭记忆回答薪资问题，报的是去年的数字。
- 数据思维：按知识域维护 staleness 窗口，超过新鲜度预算就强制走工具。

**加分项 / 常见错误：**

- 加分：按数据域定义"新鲜度策略"，而不是一刀切的"用/不用工具"规则。
- 错误：为了显得勤快对每个请求都调工具，无视成本与延迟。

#### 8. 如何让 LLM 响应在测试中足够确定？

**答题要点：**

- 分类或解析类任务设 temperature 为 0。
- 固定 prompt 与 context；测试中冻结模型和 provider 版本。
- 可用时使用 structured output 或 constrained decoding。

**面试官想听什么：**

- Trade-off：temperature 0 降低方差，但不保证跨版本、跨内核、跨 batching 的确定性；它改变的是分布，不是骰子。
- 生产反例：同一请求重试两次，即使 temperature 为 0 也返回了不同的 JSON key，因为输出契约写得不够明确。
- 数据思维：同一 eval 集跑 N 次，用编辑距离量化真实方差，再决定测试能否依赖它。

**加分项 / 常见错误：**

- 加分：区分"必须精确"（JSON key、工具名）与"可以变化"（摘要），分别断言。
- 错误：对自由文本做精确字符串相等断言，然后把 CI 抖动怪到模型头上。

### 调试

#### 9. Agent loop 在某一步之后停了，如何调试？

**答题要点：**

- 检查最后一次模型调用：tool result 畸形？schema 拒绝？还是停止条件配错？
- 用完全相同的 context 重放该步骤，追踪决策点。
- 判断失败属于解析、工具错误还是策略性停止。

**面试官想听什么：**

- Trade-off：快速失败让错误可见，但会中断可恢复的流程；重试策略用延迟换韧性。
- 生产反例：loop "停止"是因为模型输出的 action 带了个尾部换行，被严格 regex 拒绝；修法是宽容解析。
- 数据思维：按会话统计停止原因（completed、error、max steps、safety），看哪个原因占主导。

**加分项 / 常见错误：**

- 加分：做一个逐步骤重放工具，把完全相同的 context 喂回模型做离线调试。
- 错误：从零重启 loop 祈祷它能跑通，而不是复现失败的那一步。

### 设计

#### 10. 设计一个随对话变长仍保持高质量的 prompt 与 context 策略。

**答题要点：**

- 保持 system prompt 小而稳定；只增长真正重要的工作记忆。
- 对旧轮次做摘要或裁剪，把重要事实挪进结构化 state slot。
- 把当前任务和最相关的证据放在 context 的两端附近。

**面试官想听什么：**

- Trade-off：完整历史保真但费 token 且稀释注意力；摘要丢细节但便宜且聚焦。
- 生产反例：一个长程研究助手保留每一轮，准确率下降；改成滚动摘要加"关键事实"槽位后恢复。
- 数据思维：长对话与短对话分开测质量；单一平均值会掩盖退化曲线。

**加分项 / 常见错误：**

- 加分：定义明确的驱逐规则（年龄、重要性、无关性），而不是"全保留"。
- 错误：以为更大模型加更大窗口就无需 context 设计。

## 追问池

- 要一个"prompt 太模糊"的具体例子。
- 要一个"prompt 太死板"的具体例子。
- 问怎么在不损失质量的前提下降低 token cost。
- 问如果 prompt 稍微一改响应就变，他们第一步查什么。
- 问怎么向非技术同事解释 context limit。

## 常见红旗

- 把 context window 当成无限资源。
- 分不清 prompt、system instruction、tool result。
- 认为 token 数等于字符数。
- 没看 prompt 或 context 就直接建议换模型。
- 只会背定义，不会给 debug 路径。

## 作品集证据

L0 可接受的证据：

- 一个带 before/after 说明的 prompt rewrite。
- 一页 context limit 与 trade-off 说明。
- 一条展示 input、context、tool result、final response 的 tiny trace。
