# L0-L5 深度全题库

这是 Agent-Top 的 L0-L5 深度全题库。每层包含主问题、深度评分、生产级答案、追问、红旗和证据检查。

本题库参考了下面这些稳定公开来源，但真正的考察点是：候选人能不能讲清 system boundary、failure mode、trade-off 和可维护架构。

## Source Anchors

- ReAct paper：reasoning 和 acting interleaved、tool/action feedback、通过 retrieval 减少 hallucination grounding。
- MCP specification：host/client/server roles、resources、tools、prompts、transport、schema validation、error handling。
- LangGraph docs：explicit state、nodes、edges、conditional routing、checkpointing、human-in-the-loop、durable execution。
- Langfuse docs：traces、observations、prompts、evaluators、sessions、datasets、experiment reporting。
- OpenAI Agents docs：Agents、Handoffs、Guardrails、Tools、Tracing。
- NIST AI Risk Management Framework：govern、map、measure、manage 全生命周期 AI 风险。

## 面试用法

- 30 分钟快筛：问 L0、L1/L2、L4 各一道。
- 60 分钟技术 review：问 L1、L2、L3 和一个 L4 incident drill。
- 75 分钟高级 review：问 L3 design、L4 production、L5 pattern/contribution。
- Expert review：要求 answer 之外还有 evidence：traces、evals、postmortems、PRs、docs、talks。

## 评分口径

每题 0-3 分。

- 0：只有定义或背诵，没有 system boundary。
- 1：概念正确，但缺 failure mode、trade-off 或 production evidence。
- 2：能解释概念、trade-off、validation，并给一个 realistic example。
- 3：能解释概念、trade-off、failure taxonomy、measurement、rollback 或 prevention，并能接到 maintainable architecture。

## L0：基础概念

### 主问题

一个 production Agent 在 prompt 改了一个 token 后给出错误答案。请解释 prompt / system instruction / tool result / final response 的边界，并说明第一步查什么。

### 强答案必须包含

- Prompt：用户可见的 task、request 和这一轮的变量。
- System instruction：稳定的 role、policy、output contract、escalation behavior、safety rules。
- Tool result：外部 evidence 或 state，可能 stale、partial、malformed、permission-filtered，也可能和其他来源冲突。
- Final response：经过 formatting、redaction、citations、refusal handling、policy enforcement 后用户看到的输出。
- 第一步：最小 failing trace，包含 request、system prompt、retrieved context、tool calls/results、model output、parser/finalizer behavior、latency、cost。

### 深度追问

- Token 如何影响 cost、latency、behavior？为什么 character count 不够？
- 如何区分 context overflow 和 model hallucination？
- 如何防止 prompt edit 悄悄改变 tool-call policy？
- 如何在 logs 里保留 prompt version、model version、tool schema version？

### 生产证据

要求候选人给一个 tiny trace 或 prompt rewrite，展示：

- Before/after prompt。
- System instruction version。
- Tool result source 和 timestamp。
- Final response。
- Root cause category。

### 红旗

- 把 prompt、system instruction、tool result 当成可互换文本。
- 先看 trace 和 inputs 之前就说“换模型”。
- 不能说清 tool output 为什么还要 validation。
- 混淆 raw model output 和 final user response。

### Source-Informed Notes

ReAct 的关键不是“会思考”，而是 reasoning、action、observation 可以形成可追踪闭环。L0 答案应该已经体现这一点。

## L1：Agent 组件和 Loop 控制

### 主问题

用代码视角设计一个最小 ReAct Agent：state、actions、observations、stop conditions、logs、failure handling。

### 强答案必须包含

- State：goal、messages/context、available tools、observations、plan/next action、attempts、policy status、cost/latency counters。
- Actions：answer、ask clarification、call tool、retrieve evidence、escalate、stop、rollback/abort。
- Observations：tool success/failure、empty result、timeout、permission denial、schema mismatch、partial data、duplicate repeated observation。
- Stop conditions：success、max steps、max cost/latency、repeated failure、ambiguity、policy violation、unsafe intent、missing evidence。
- Logs：step number、plan/action、tool name、args hash、result summary、stop reason、prompt/model/tool schema versions、trace ID。

### 深度追问

- 为什么必须有 max step limit？达到后正确行为是什么？
- Tool result 是 valid JSON 但语义错误，怎么处理？
- 如何防止 retrieved document 里的 prompt injection 改变 tool policy？
- 如何在 direct answer、tool call、clarification、escalation 之间决策？

### 生产证据

要求给出 pseudocode sketch 或 Lab result，Agent 能：

- 重复相同 tool call 后停止。
- 不确定时 clarify，而不是猜。
- 记录足够细节以便重建 decision。
- 没有 approval 不执行 destructive action。

### 红旗

- 把 ReAct 当成 prompt template。
- 没有 stop condition 或 failure budget。
- 直接把完整 tool result 给 model，没有 size、privacy、schema check。
- 分不清 model planning 和 tool execution。

### Source-Informed Notes

ReAct-style Agent 把 reasoning trace 和 external action 组合起来。工程关键问题是：系统能否 observe actions、safely stop、replay trace。

## L2：框架、Tools、MCP 和边界

### 主问题

为可靠单 Agent 设计 tool layer：MCP-style tools、validation、permissions、failure taxonomy、human approval。

### 强答案必须包含

- Tool contract：name、description、input schema、output schema、timeout、retryability、risk level、required permissions、audit requirements。
- MCP layering：host owns Agent policy；client manages server connection；server exposes resources/tools/prompts；transport 可为 stdio、SSE、streamable HTTP 或等价方案。
- Discovery：server health、tool list、prompts/resources、schema version、auth scopes、capability changes。
- Invocation：validate inputs、enforce risk policy、call tool、classify errors、validate outputs、normalize evidence、store trace。
- Risk classes：read-only、write reversible、write irreversible、payment-like、permission-changing、data-export、destructive、policy-sensitive。
- Human approval：irreversible writes、high blast radius、permission changes、ambiguous intent 时必须确认。

### 深度追问

- 如何区分 discovery failure、auth failure、schema mismatch、timeout、application failure？
- Server 返回 valid output 但来自 wrong tenant，怎么处理？
- 如何 rate-limit 和 retry，同时不放大伤害？
- 如何防止 tool schema change 悄悄改变 Agent behavior？
- 什么情况下用 framework orchestration，什么情况下用 plain SDK/plain loop？

### 生产证据

要求 tool-call trace 包含：

- Tool name 和 schema version。
- Permission decision。
- Input validation result。
- Output validation result。
- Retry/timeout policy。
- Approval 或 audit record。

### 红旗

- 让 model output 直接 call tools，没有 validation。
- 把 MCP 当“又一个 API”，没有 schema、transport、error handling。
- 不管风险都人工确认。
- 解释不了 schema mismatch 或 auth-scope failure。
- 小 loop 能讲清楚时还用重型 framework。

### Source-Informed Notes

MCP 定义了 client/server capabilities 和 schema-validated messages。强候选人会把 MCP 当 governed tool boundary，而不是绕过 validation 的快捷方式。

## L3：端到端系统设计

### 主问题

设计一个客服 Agent：RAG、memory、tools、MCP-style actions、observability、evals、human escalation。

### 强答案必须包含

- Requirements：traffic、latency、accuracy、privacy、language/region、compliance、cost、audit、rollback、support SLA。
- Trust boundaries：user、tenant、document corpus、ticket system、order system、human reviewer、Agent runtime。
- Data flow：intake -> intent/policy check -> retrieval -> memory lookup -> tool routing -> answer synthesis -> validation/citations -> final response -> trace。
- Retrieval：tenant/user/time/version scoped；包含 chunking、ranking、filters、reranking、freshness、abstention。
- Memory：短期 conversation state 和长期 preferences/facts 分离；包含 TTL、owner、deletion、consent、conflict handling、staleness checks。
- Tools：order lookup、ticket update、refund proposal、policy lookup、escalation，以及带 approval 的 write actions。
- Evals：retrieval relevance/recall、answer support、citation correctness、refusal quality、tool accuracy、escalation accuracy、latency、cost、safety。
- Observability：trace 每个 prompt、retrieved source、memory read/write、tool call、decision、citation、final response、cost、stop reason。

### 深度追问

- 如何知道 final answer 来自 RAG、memory、live tool state 还是 model？
- 如何防止一个 Agent 覆盖另一个 Agent 的 decision 或 shared state？
- 什么时候 refuse、retrieve more、call tool、escalate？
- Policy docs 冲突、memory stale 时怎么处理？
- 如何评估“不应回答”的 negative cases？

### 生产证据

要求一页 design 或 whiteboard trace，展示：

- Request。
- Retrieved docs 和 timestamps。
- Memory read/write decision。
- Tool call 和 result。
- Citation 或 refusal。
- Final answer。
- 为已知 failure 新增的 eval/regression case。

### 红旗

- 没有 decomposition 或 ownership 就上来 multi-agent。
- 忘记 tenant isolation、citations、refusal、stale memory。
- 把 retrieval 当“把所有东西塞进 context”。
- Launch 前没有 eval strategy。
- 没有 tool failure 或 human escalation 路径。

### Source-Informed Notes

最强 L3 答案会像 trace 一样讲系统：证据从哪里来、状态谁拥有、哪里会失败、系统如何证明答案正确且安全。

## L4：生产可靠性、安全和运营

### 主问题

客户说 Agent 改错了账户。请主持 incident response，并定义防止复发的 release gate。

### 强答案必须包含

- Containment：disable 或 route around risky action path；data integrity 不确定时 freeze writes。
- Evidence collection：request ID、trace ID、prompt/system version、model version、retrieved context、memory、tool schema、tool args/results、authorization、user role、tenant、final response、rollout metadata。
- Root cause categories：bad data、retrieval miss、stale memory、wrong tool schema、malformed output、permission bypass、model behavior change、parser/finalizer bug、prompt regression、rate/cost anomaly、human approval gap。
- Communication：customer impact、internal severity、affected tenants、rollback status、next update time、owner。
- Fix：patch code/prompt/schema/tool policy，加 eval 和 trace field，加 guardrail，写 postmortem 并明确 owner 和 due date。
- Prevention：release gate 包含 golden evals、safety evals、tool-schema contract tests、authorization tests、trace completeness、rollback plan、canary/shadow deployment。

### 深度追问

- 这应该是什么 severity？为什么？
- 哪个 canary signal 本应在全量前抓住它？
- 如何判断 guardrail 太严还是太松？
- Model version change 如何作为 release 处理？
- 如何按 correctness、safety、data integrity、privacy、availability、cost 分类 incident？
- 如何在避免敏感数据泄露的同时让 traces 仍然有用？

### 生产证据

要求 postmortem-style artifact，包含：

- Timeline。
- Root cause。
- Detection path。
- Customer/user impact。
- Rollback。
- Regression eval。
- Owner 和 due date。
- Non-goals 和 residual risk。

### 红旗

- 不看 data、prompts、tools、traces 就怪 model。
- 没有 containment step。
- 没有 rollback plan。
- 没有 regression eval 或 prevention control。
- 把 observability 当 final logs，而不是 replayable traces。

### Source-Informed Notes

NIST AI RMF 把 AI 风险框架化为 govern、map、measure、manage。incident 答案应该能 map failure、measure impact、contain risk，并用 evals 和 release gates manage residual risk。

## L5：专家模式、贡献和生态策略

### 主问题

提出一个值得贡献给 Agent-Top 的原创 Agent pattern，包含 contract、failure modes、evals、migration story、impact evidence。

### 强答案必须包含

- Problem：跨系统重复出现的 failure 或 maintenance pain，而不是 framework flavor。
- Pattern contract：inputs、outputs、state、tools、memory、stop conditions、safety boundaries、observability、validation。
- Failure taxonomy：哪里会失败、如何检测、fallback 是什么。
- Evals and traces：可能时用 deterministic tests，再加 golden cases、negative cases、latency/cost baselines、replayable trace fields。
- Adoption story：什么时候用、什么时候不用、如何从现有代码迁移、deprecation policy、maintainer burden。
- Evidence：Lab、PR、talk、article、design review、external adoption、measurable improvement。
- 规范先行起草：提示前用 [Vibe Coding 工作流](../../vibe-coding/README.md) 用一句话写清目标、接口与验收。

### 深度追问

- 你 rejected 了什么？为什么？
- 什么让它成为 pattern，而不是 framework wrapper？
- 如何防止 framework churn 让 pattern stale？
- Lab 什么时候应该 graduate 到 production guidance？
- 如何在 pattern abstraction 和 easy understanding 之间平衡？
- 什么证据会让 maintainers 拒绝这个 contribution？

### 生产证据

要求其一：

- 带 tests 和 docs 的 Lab 或 PR。
- 有 rejected alternatives 和 migration steps 的 pattern note。
- 有 trade-offs 的 design review。
- talk、article 或 community artifact。
- measurable result：更少 incident、更低 cost、更好 eval score、更快 onboarding、更少 manual review。

### 红旗

- 贡献只是 framework example。
- 没有 failure modes 或 negative cases。
- 没有 migration 或 deprecation story。
- 只有 usage examples 就声称 L5 impact。
- 解释不了 maintainer burden 或 ecosystem fit。

### Source-Informed Notes

强 L5 会借鉴成熟项目但不复制。它 pattern first、frameworks second，并用 tests、docs、traces、contribution evidence 证明价值。

## 深度答案检查清单

完整答案应包含：

- System boundary。
- Trust boundary。
- Data 或 evidence path。
- Tool/action policy。
- Failure taxonomy。
- Stop 或 escalation condition。
- Observability 和 trace fields。
- Eval 或 regression case。
- Rollback 或 prevention。
- Trade-off 和 rejected alternative。
- 一个 concrete example。

## 深度追问库

- 什么数据会让这个答案错？
- 最便宜的 safe rollback 是什么？
- 哪个 trace field 会暴露 root cause？
- 哪个 eval 会 block 这次 bad release？
- 即使 model 很自信，哪些动作也不应自动执行？
- Tool schema 变了怎么办？
- Memory 和 retrieval 冲突怎么办？
- User 要求 irreversible action 怎么办？
- 什么指标能说明 guardrail 太严？
- 什么 evidence 能说服 maintainer 这应该 upstream？

## Level-to-Evidence Mapping

| Level | Best Evidence |
| --- | --- |
| L0 | Prompt rewrite、tiny trace、token/context budget note |
| L1 | Minimal ReAct Lab、stop-condition test、tool ambiguity test |
| L2 | Tool schema contract、MCP failure taxonomy、approval trace |
| L3 | 带 RAG/memory/tools/escalation 和 eval matrix 的 system design |
| L4 | Incident postmortem、regression eval、rollback plan、trace example |
| L5 | Original pattern、Lab/PR、migration story、external contribution |
