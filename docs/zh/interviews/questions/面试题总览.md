## 面试组合

### 45 分钟 Agent Engineer Screen

用于核心实现能力筛选。

- L1: 解释 Agent 四个组件。
- L1: ReAct 为什么需要 max step limit。
- L2: 好的工具边界。
- L2: MCP integration failure 怎么排查。
- 结尾要求展示一个 runnable ReAct 或 tool-use demo。

通过信号：能分清 perception、planning、tools、memory；能补 stop condition；先要 failure logs 再判断。

### 60 分钟 Mid-Level Technical Interview

用于 framework、tool integration 或 single-Agent reliability。

- L2: framework vs lightweight SDK。
- L2: 按风险决定 human confirmation。
- L3: RAG + memory + MCP data flow。
- L4: pre-release checklist。
- Follow-up: model version change as release。

通过信号：选择 failure modes 显式的简单架构，并能连接 traces、evals、rollback。

### 75 分钟 Senior System Design

用于 production-facing Agent systems。

- L3: 设计多 Agent 客服系统。
- L3: retrieval agent launch 前评估。
- L4: 错误账户变更事故。
- L4: cost/quality trade-off。
- L5: high-risk tool execution pattern。

通过信号：不靠提示也能讲 permissions、error isolation、observability、rollback、prevention controls。

### 90 分钟 Expert Review

用于 L5、staff/principal 或开源贡献者 review。

- L5: 有价值的 reusable Agent pattern。
- L5: build vs use framework。
- L5: 防止 framework churn 破坏 docs。
- L5: 证明 expert capability 的 OSS contribution。
- 加 STAR: 一个生产 incident、一个 contribution、一个 mentoring/review story。

通过信号：能讲 durable pattern、rejected alternatives、maintenance cost、external evidence。

## Common Red Flags

- 先说框架名，再说 system problem。
- 默认 tool output 可信。
- 使用 long-term memory 但不讲 scope、freshness、privacy、deletion。
- 为了多 Agent 而多 Agent，没有 decomposition reason。
- launch 后才想起 evals。
- writes、payments、deletes、permission changes 没有 rollback path。
- 答案漂亮但不能解释 trace、logs、failure boundary。

## 评分口径

每题 0-2 分：

- 0: 背概念或泛泛而谈，没有 system boundary。
- 1: 概念正确，但缺 production trade-off 或 failure path。
- 2: 有答案、trade-off、measurement、rollback，并给出 concrete example。

建议阈值：

- L1-L2 通过：所有必问题至少 1，安全类问题不得 0。
- L3-L4 通过：80% 问题达到 2，incident/rollback 必须 2。
- L5 通过：original pattern 或 contribution 达到 2，且 evidence 不止 usage。

## 下一批扩展计划

### 建议新增 20 题

- L1: tool ambiguity、memory staleness、planning stop conditions、direct-answer vs tool-call。
- L2: MCP capability discovery、tool schema mismatch、auth scopes、provider SDK migration。
- L3: stale memory、multi-source citation、retrieval refusal、multi-agent state ownership。
- L4: incident severity、cost anomaly、rate limit handling、model canary、trace privacy。
- L5: original pattern contribution、framework deprecation policy、cross-team governance、docs-as-product。

### 优先级

1. 加深 L2 MCP 和 tool security。
2. 增加 L4 incident drills，要求明确 root-cause categories。
3. 增加 L5 contribution 和 governance 题，并要求 portfolio evidence。
4. L0 的 production variants 等基础页稳定后再补。

## 候选人准备清单

- 跑一个 L1 Lab，并口头解释 loop。
- 展示一条 tool-call trace，包含成功和失败 case。
- 准备一个 RAG 或 memory 设计，包含 citations 和 refusal behavior。
- 准备一个 production incident，包含 root cause、rollback、prevention eval。
- 准备一个 contribution STAR story，并链接到 pattern quality。
