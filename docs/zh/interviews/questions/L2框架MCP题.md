# L2 框架和 MCP 题

这一组题考察框架判断力、MCP 协议推理，以及单个生产 Agent 的可靠性工程。

## 题库

覆盖四类题型：概念、实现、调试、设计。

### 概念

#### 1. 如何选择 graph orchestration 还是 lightweight SDK？

**答题要点：**

- 复杂状态、循环、checkpoint、human review 用 graph orchestration。
- 小型线性、容易调试的流程用 lightweight SDK。
- 选择能让 failure modes 显式化的最简单方案。

**面试官想听什么：**

- Trade-off：编排框架用间接层和调试开销换 checkpoint 与可恢复性；SDK 透明但状态和重试要自己写。
- 生产反例：一个团队把三步线性 RAG 流程迁进图框架，步数翻了三倍；只有真正需要崩溃恢复后，持久 checkpoint 才值回票价。
- 数据思维：统计流程崩溃后需要恢复、或被打断后继续的频率；这个频率而不是功能清单决定编排税值不值。

**加分项 / 常见错误：**

- 加分：说出真正拍板的框架特性，比如持久 checkpoint 或 human-in-the-loop 暂停点。
- 错误：因为品牌熟悉或 demo 好看就选框架，而不是基于实测失败模式。

#### 2. 什么是 MCP，它解决什么问题？

**答题要点：**

- MCP 标准化 Agent 发现、连接、调用能力的方式，是一套协议。
- 它把 tool、resource、prompt server 定义与 Agent 运行时分离。
- 它用一套协议（发现、schema、auth）替代 N 个临时拼的 API 集成。

**面试官想听什么：**

- Trade-off：标准降低集成成本、支持复用，但新增协议层、发现开销和需要维护的版本化面。
- 生产反例：一家公司有 40 个定制工具集成，团队间无法共享；MCP 式 server 砍掉了大量按应用写的集成，但前提是先统一 auth 和命名约定。
- 数据思维：采用前数一下集成数量、维护工时和工具形状变更频率；矩阵大且共享多时标准才划算。

**加分项 / 常见错误：**

- 加分：说明 MCP 是 Agent-工具边界的协议，不是 agent 框架；transport、auth、版本化仍需设计。
- 错误：把 MCP 当魔法层，以为有了它就不需要 schema 质量和安全审查。

#### 3. 如何选 graph orchestration、multi-agent 还是 lightweight？

**答题要点：**

- graph orchestration 适合复杂、可恢复、有人审的流程。
- multi-agent 适合有清晰交接的独立专家，但要付出协调成本。
- lightweight SDK 或 plain loop 适合小线性流程，透明胜过机制。

**面试官想听什么：**

- Trade-off：multi-agent 成倍放大失败面（错误交接谁负责？）和 token 成本；两个 Agent 可能比一个结构良好的 loop 更贵更不可靠。
- 生产反例：一个"planner、writer、reviewer"三 Agent 管线劣化，因为 reviewer 把正确成果重写了；合并成单 Agent 加 checkpoint 和审查门，质量恢复且成本下降。
- 数据思维：测量每多一个 Agent 的边际价值（每 token 的质量增益）；第二个 Agent 增益低于成本就砍掉。

**加分项 / 常见错误：**

- 加分：按失败域决策——状态复杂度、并行度、专业化，而不是赶时髦。
- 错误：把 "multi-agent" 当口号，却不定义交接契约或问责。

### 实现

#### 4. 什么是好的工具边界？

**答题要点：**

- 一个工具一个职责，输入输出类型化并校验。
- 副作用要显式；错误必须能与空结果区分。
- 破坏性动作需要确认或审批，返回足够审计的元数据。

**面试官想听什么：**

- Trade-off：粗粒度工具减少往返但输出臃肿、失败噪声大；细粒度工具可组合但消耗更多模型步骤。
- 生产反例：一个"管理一切"的工具让模型在用户想暂停订阅时取消了订阅；拆成 read、update、cancel 三个带明确范围的工具修好。
- 数据思维：跟踪每个工具的误用率，用数据驱动边界调整，而不是凭直觉。

**加分项 / 常见错误：**

- 加分：给每个工具写效果契约：输入、副作用、"完成"是什么意思。
- 错误：返回格式正确但数据错误的响应——最难发现，因为它看起来像成功。

#### 5. 如何让单个 Agent 在生产里不再不可靠？

**答题要点：**

- 在模型之外加代码强制的停止条件、schema 校验、重试与超时策略。
- 对破坏性动作加 guardrail，对停止原因和失败分布加告警。
- 让每一步都能用精确输入输出重放，支撑事后分析。

**面试官想听什么：**

- Trade-off：可靠性控制改进行为但减少灵活性；每个 guardrail 都增加延迟，还可能误伤合法场景。
- 生产反例：一个拒绝任何 schema 偏差的解析器让 Agent 看起来坏了一周，直到团队发现 60% 的"失败"只是一个可选字段缺失。
- 数据思维：把可靠性当分布看（停止原因、重试、工具错误），对偏移告警，而不是对单次失败告警。

**加分项 / 常见错误：**

- 加分：区分"硬可靠性"（崩溃、挂起、预算）与"软质量"（答错），分开监控。
- 错误：承诺固定成功率，却不记录能解释任何一次失败的数据。

#### 6. MCP server integration 失败，如何排查？

**答题要点：**

- 先查 server availability 和 transport，再查 schema 与 capability discovery。
- 再查 auth 与权限，然后检查第一次工具调用的日志。
- 把失败分类：discovery、invocation、timeout、permission 还是 output parsing。

**面试官想听什么：**

- Trade-off：宽超时把慢 server 藏在模糊失败后面；紧超时在流量尖峰时制造假警报——按能力维度单独定预算。
- 生产反例：一次"server down"告警其实是 schema 版本错配：server 提供的工具，客户端还按旧版本缓存，每次调用都校验失败。
- 数据思维：按 server 记录协议错误码和延迟分位数；P99 延迟漂移通常先于第一个用户可见失败出现。

**加分项 / 常见错误：**

- 加分：加健康探针，并通过真实工具调用路径做回环测试，保证生产可见性。
- 错误：transport 或 capability discovery 才是真凶时，却在应用层排查。

#### 7. 工具返回有效数据但结果错误，怎么处理？

**答题要点：**

- 区分 schema 合法与语义正确。
- 加期望范围检查、与第二来源交叉验证、或新鲜度检查。
- 把信号作为显式"unverified"状态交给 Agent，升级人工审查。

**面试官想听什么：**

- Trade-off：全量验证成本和延迟翻倍；抽样验证能抓住系统性 bug 而不拖累每次调用。
- 生产反例：货币工具返回形状正确但单位错误的数值；schema 校验通过了几个月，直到与第二个 provider 交叉验证才发现。
- 数据思维：在样本上对比便宜检查（类型、范围、单位）与 ground truth 的不一致率；不一致率不为零就需要常开的 spot check。

**加分项 / 常见错误：**

- 加分：给每个工具结果加 source 和 timestamp 字段，下游才能验证。
- 错误：把 schema 校验成功当成数据正确。

### 调试

#### 8. 生产里 MCP 工具调用超时，如何排查？

**答题要点：**

- 确认超时发生在客户端、transport、server 端还是工具下游。
- 查延迟分位数、重试行为，以及超时后工具到底执行了没有。
- 加幂等键，避免重试重复执行副作用。

**面试官想听什么：**

- Trade-off：重试修复瞬时故障，但对非幂等工具很危险；超时约束延迟，但留下"到底执行没有"的模糊。
- 生产反例：一次近似支付的调用超时，Agent 重试，动作被执行了两次，因为工具不幂等。
- 数据思维：统计 timeout-to-success 比例（调用失败但副作用发生），据此决定何时重试安全。

**加分项 / 常见错误：**

- 加分：要求所有状态变更型 MCP 工具接受幂等键。
- 错误：默认超时就是没执行。

#### 9. 如何让 MCP 集成失败在生产里可见？

**答题要点：**

- 暴露健康探针、结构化协议错误码、按 server 的延迟分位数。
- 记录完整往返：请求、transport、响应、实际使用的 schema。
- 对比率偏移（错误率、P99 延迟）告警，而不是对单次失败告警。

**面试官想听什么：**

- Trade-off：丰富日志让诊断即时但费存储；重负载抽样，元数据全保留。
- 生产反例：集成"staging 好好的，prod 挂了"，因为 prod 用了不同 transport 和 auth 路径；修法是走真实协议的 prod 对齐测试。
- 数据思维：每次调用记录 schema 版本和错误码，版本错配失败才能归因。

**加分项 / 常见错误：**

- 加分：做 canary 调用，定时跑真实工具路径。
- 错误：对原始错误计数告警，被单个用户反复重试吵醒。

### 设计

#### 10. 为接触外部系统的 Agent 设计 guardrail 策略。

**答题要点：**

- 策略用代码强制，不只在 prompt 里：允许的动作、允许的目标、限流、审批门。
- 按可逆性、爆炸半径、数据敏感度分级。
- 用 correlation ID 写审计日志，执行后验证。

**面试官想听什么：**

- Trade-off：严格的代码门安全但有摩擦；宽松的发布快但漏风险——按风险类别调，不要一刀切。
- 生产反例：一个"安全"的审批组件被绕过，因为同一 UI 元素同时服务不同动作类型的预览和确认；按动作类别分开确认契约才堵住。
- 数据思维：把 guardrail 触发率、覆盖率和绕过尝试率当产品指标跟踪，而不只是安全指标。

**加分项 / 常见错误：**

- 加分：guardrail 是外圈，system prompt 只是内圈便利，永远不是唯一屏障。
- 错误：对不可逆后果的动作只靠一句 refusal prompt。

#### 11. 设计一个决策框架：什么时候从单 Agent 迁到 graph orchestration 或 multi-agent？

**答题要点：**

- 用实测信号决策：崩溃恢复频率、人工审查点、并行机会、每 Agent 专业化增益。
- 在重放、checkpoint 或审查需求被证明之前，保持单 Agent。
- 拆分前先定义交接契约和问责。

**面试官想听什么：**

- Trade-off：拆分改善模块化与并行，但提高协调、token 和调试成本。
- 生产反例：报告管线拆成 researcher 和 writer 两个 Agent 后章节互相矛盾，直到加了共享事实状态和审查门。
- 数据思维：同一 eval 集上对比各流程变体的质量与成本；按数字选，不按架构图选。

**加分项 / 常见错误：**

- 加分：先跑"单 Agent 加 checkpoint"基线，测出差距再采用任何框架。
- 错误：数据还没显示单 loop 是瓶颈，就先拆 Agent。

## 追问池

- 什么框架特性会迫使你放弃 plain loop 选 graph orchestration？
- 如何让 MCP 集成失败在生产里可见？
- 你会为高风险支持操作设计什么样的审批流程？
- 什么时候单 Agent 加 checkpoint 优于 multi-agent？
- 如何验证一个 schema 合法但语义错误的工具结果？

## 常见红旗

- 凭 hype 选框架或多 Agent，而不是凭实测失败模式。
- 把 MCP 当 agent 框架，而不是工具边界的协议。
- 安全关键约束只信 prompt。
- 把 schema 校验当成数据正确性的证明。
- 生产里没有重放路径，也没有停止原因数据。

## 作品集证据

L2 可接受的证据：

- 一份把实测系统需求映射到具体选型的框架选择说明。
- 一个带健康探针、结构化错误码、完整回环 trace 的 MCP server。
- 一份覆盖停止原因、重试和 guardrail 指标的单 Agent 可靠性报告。
