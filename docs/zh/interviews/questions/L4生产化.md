# L4 生产化

这些问题考察候选人能否在生产中运营 Agent 系统：发布门禁、评估体系、可观测性、安全护栏、成本控制和事故后学习。覆盖概念、实现、调试、设计四类题型。

## 题库

### 概念

#### 1. 上线 Agent 功能前你要做什么？

**答题要点：**

- 按角色和租户定义认证与权限。
- 速率限制和成本护栏存在且有负责人。
- 评估集全绿，包含负例和安全用例。
- 可观测性记录 prompt、工具、答案、延迟和成本。
- 回滚计划已文档化并演练过。

**面试官想听什么：**

- Trade-off：什么都拦的门禁和什么都不拦的门禁一样糟糕；把每项检查分类为 block、warn 或 require-approval。
- 生产反例：只覆盖 happy path 的评估集全绿时，护栏已回归；门禁通过是因为失败用例根本不在集里。
- 数据思维：基于可测量的变化发布——解决率、每任务成本、护栏触发率的前后对比——而不是凭感觉。

**加分项 / 常见错误：**

- 加分项：指出单独一项就能阻止发布的东西（通常是安全评估或回滚演练）。
- 常见错误：demo 跑通就上线，评估套件可有可无。

#### 2. 评估集和可观测性 trace 有什么区别？

**答题要点：**

- 评估集是离线、版本化的输入套件，带期望行为，每次变更都运行。
- trace 是生产中每次请求实时发生什么事的记录。
- 评估在发布前拦截回归；trace 在发布后诊断事故。
- 两者在回放处汇合：生产 trace 失败时可转化为评估用例。

**面试官想听什么：**

- Trade-off：评估覆盖越多，CI 成本和维护越高；trace 越多，存储成本越高。把预算花在失败模式所在处。
- 生产反例：团队 trace 很丰富但没有评估，一周的事故之后才发现回归，因为没人把过去的失败回放进测试套件。
- 数据思维：追踪评估-事故比——每个生产事故至少应增加一个评估用例；这个比例是领先健康指标。

**加分项 / 常见错误：**

- 加分项：黄金集版本化和 trace schema 版本化，回放保持准确。
- 常见错误：把仪表盘当成评估门禁的替代品。

### 实现

#### 3. 如何构建 Agent 评估体系？

**答题要点：**

- 从版本化黄金集开始，含事实、拒绝、安全和模糊用例的期望行为。
- 分层度量流水线：检索（recall@k）、工具选择（准确率）、生成（支持度、faithfulness）、最终答案（引用准确度）。
- 在 CI 中加自动化检查：确定性单元检查加带固定 rubric 的模型评分。
- 追踪每用例的延迟与成本；10 倍成本换来的质量增益未必能上线。
- 保留回归门禁：任何 prompt、模型或工具变更都必须重跑评估集。

**面试官想听什么：**

- Trade-off：模型评分可扩展但可能宽松或漂移；确定性检查稳定但漏语义错误。结构用确定性检查，语义用模型评分，并对样本人工审计。
- 生产反例：赞扬"自信且有用"的 rubric 放过了幻觉；修复是要求证据接地作为硬性通过/失败维度。
- 数据思维：分别度量误拒绝与误接受，并按租户、语言、主题切片找薄弱段。

**加分项 / 常见错误：**

- 加分项：评估 trace 回放——每个生产失败都变成永久回归用例。
- 常见错误：只测最终答案，忽略错误来自流水线哪一层。

#### 4. 如何让 Agent 行为在生产中可观测？

**答题要点：**

- 每个请求输出结构化 trace：prompt、上下文、工具调用、决策、停止原因、延迟、成本和评估结果。
- 用关联 ID 把 trace 关联到用户、租户和功能。
- 追踪指标：请求量、成功/拒绝/升级率、p50/p95/p99 延迟、每任务成本、工具错误率。
- 记录停止原因（answer、clarify、escalate、exhausted），让循环问题可见。
- trace 保留足够长以便回放事故，并做 PII 脱敏。

**面试官想听什么：**

- Trade-off：完整 trace 存储贵；对重负载抽样，但保留完整元数据和脱敏内容。
- 生产反例：trace 停在最终答案，错误退款无法回放；补上工具调用和决策 span 后，根因几分钟内可见。
- 数据思维：仪表盘展示停止原因分布——"exhausted"占比上升意味着循环在烧预算，而不是在提升满意度。

**加分项 / 常见错误：**

- 加分项：按计划跑真实工具路径的金丝雀 trace。
- 常见错误：对原始错误计数告警，为一个噪声重试把人叫醒。

### 调试

#### 5. 客户报告 Agent 做了错误的账户变更。

**答题要点：**

- 立即停止不安全动作路径；冻结受影响工具或用户队列。
- 检查 trace：prompt、检索上下文、工具调用参数和决策路径。
- 在数据、工具 schema、策略或权限边界中找根因——而不只是模型。
- 添加回归评估和预防控制（权限规则、schema 校验、确认门禁）。
- 写 postmortem，含负责人、截止日期、回滚计划和预防清单。

**面试官想听什么：**

- Trade-off：修复速度与根因完整性之间权衡；先止血，但关闭事故前必须有回归用例。
- 生产反例：团队加一行 prompt 就"修复"了错误退款；因为权限边界仍缺失，同样的错误再次发生。
- 数据思维：把事故关联到指标——哪个租户、哪个工具、哪种参数形态——让修复有范围、评估用例对准真实失败。

**加分项 / 常见错误：**

- 加分项：在事故前演练回滚，而不是事故中。
- 常见错误：怪模型、回退 prompt，却不审计工具和权限层。

#### 6. 如何为 Agent 事故做 postmortem？

**答题要点：**

- 用数字说明对用户和业务的影响。
- 时间线：改了什么、什么时候、trace 显示什么。
- 组件级根因：数据、模型、工具、策略或部署。
- 促成因素：缺评估、缺告警、所有权不清。
- 带负责人和截止日期的行动：预防、检测、恢复。
- 跟进：验证每个行动已上线，并为复发添加评估用例。

**面试官想听什么：**

- Trade-off：无指责 postmortem 得到更好的数据；指责得到沉默。把人为错误与系统设计缺口分开。
- 生产反例：怪"模型"的 postmortem 没有产生行动项；重新表述为缺失接地检查后产生了真正的修复。
- 数据思维：每个 postmortem 至少改变一个评估用例、一个告警和一个所有权边界；追踪这个三项闭环。

**加分项 / 常见错误：**

- 加分项：公开 postmortem 模板，含影响、时间线、根因、行动。
- 常见错误：写没有负责人和截止日期的 postmortem——那是日记，不是流程。

### 设计

#### 7. 为会触达外部系统的 Agent 设计安全护栏。

**答题要点：**

- 用代码而非只靠 prompt 强制策略：允许的动作、允许的目标、速率限制、审批门禁。
- 按可逆性、爆炸半径和数据敏感性分类风险；每个动作映射到风险等级。
- 执行前校验参数 schema；不可逆动作要求确认。
- 带关联 ID 输出审计日志，执行后验证。
- 让护栏成为外环；系统 prompt 只是内层便利，绝不是唯一屏障。

**面试官想听什么：**

- Trade-off：严格代码门禁安全但有摩擦；宽松的交付快但漏风险。按风险等级调节，而不是全局一刀切。
- 生产反例：一个"安全"审批组件被绕过，因为同一 UI 元素为不同类型动作同时服务预览和确认；按动作类分离确认契约后堵住了。
- 数据思维：把护栏触发率、覆盖率和绕过尝试率当作产品指标追踪，而不只是安全指标。

**加分项 / 常见错误：**

- 加分项：每个变更类工具带幂等键，加执行后验证。
- 常见错误：对不可逆后果的动作只依赖拒绝 prompt。

#### 8. 如何在生产 Agent 中平衡成本与质量？

**答题要点：**

- 按难度路由：路由和常见用例用小模型，复杂推理用大模型。
- 缓存稳定检索和模板答案；按新鲜度策略失效。
- 设置每请求预算：最大步数、最大 token、墙钟截止、最大工具调用数。
- 监控每任务和每租户成本；对异常告警。
- 先优化循环再加模型：减少冗余工具调用、改进停止条件，往往比换大模型更有效。

**面试官想听什么：**

- Trade-off：大模型提升质量但成倍增加成本和延迟；切换前先在评估集上度量质量差。
- 生产反例：团队把模型大小翻倍，评估分数几乎没动，因为瓶颈是检索质量，不是推理。
- 数据思维：绘制质量对每任务成本的曲线；前沿曲线决定是花更多 token 还是修流水线。

**加分项 / 常见错误：**

- 加分项：任何模型切换前先做带成本追踪的影子流量。
- 常见错误：只优化 token 成本却忽略延迟和支持负担——最便宜的失败答案并不便宜。

## 追问池

- 哪一项会单独阻止发布？
- Agent 系统中好的事故根因长什么样？
- 如何决定用阻断门禁还是警告门禁？
- 什么时候缓存工具结果，什么时候实时调用？
- 如何证明回归修复真的防止了复发？

## 常见红旗

- 没有评估集，或评估集从不变化。
- 把仪表盘当成评估门禁。
- 安全只在 prompt 里强制。
- 没有回滚计划，或回滚计划从不演练。
- postmortem 没有负责人或行动项。

## 作品集证据

L4 可接受的证据是：

- 带版本化黄金集和 CI 回归门禁的评估报告。
- 含影响、时间线、根因和已验证行动的事故 postmortem。
- 覆盖回滚、降级模式和值班流程的生产 runbook。
- 展示每任务成本、延迟与质量权衡决策的成本报告。
