# L3 系统设计题

这些问题考察候选人能否以生产视角设计、调试和评估 Agent 系统：组件边界、故障隔离、成本与延迟、以及基于证据的决策。覆盖概念、实现、调试、设计四类题型。

## 题库

### 概念

#### 1. 什么时候用多 Agent，什么时候用单 Agent？

**答题要点：**

- 当拆分能提升清晰度、权限隔离或专门化，且独立验证能带来真实价值时，优先多 Agent。
- 当任务小、延迟紧、或协调成本超过可靠性收益时，优先单 Agent。
- 只有独立检查能发现单循环遗漏的错误时，才加验证 Agent。
- 在加第二个 Agent 之前先定义交接契约：消息 schema、所有权和错误语义。

**面试官想听什么：**

- Trade-off：多 Agent 放大了故障面（错误交接谁负责？）和 token 成本；两个 Agent 可能比一个结构良好的循环更贵、更不可靠。
- 生产反例："planner、writer、reviewer" 流水线因为 reviewer 重写了正确的工作而退化；合并为带检查点和审查门禁的单 Agent 反而修复了质量并降低成本。
- 数据思维：度量每个新增 Agent 的边际价值（每 token 的质量增益）；如果第二个 Agent 的增益低于成本，就砍掉。

**加分项 / 常见错误：**

- 加分项：按失败域决策——状态复杂度、并行度、专门化——而不是追热点。
- 常见错误：把"多 Agent"当流行词，却不定义交接契约或问责制。

#### 2. 你怎么知道最终答案来自 RAG、记忆还是实时工具状态？

**答题要点：**

- 要求 provenance 元数据：每个论断标注来源类型、来源 ID 和时间戳。
- 强制执行接地检查（grounding check）：标记没有检索或工具证据支撑的论断。
- 分离存储：记忆（用户事实）不得与知识（文档）或实时状态（工具结果）混用。

**面试官想听什么：**

- Trade-off：provenance 消耗存储和 prompt token，但让每个答案可审计、每个事故可回放。
- 生产反例：答案引用了缓存文档而账单状态已变；没有来源标签，没人能说出哪一层过期了。
- 数据思维：追踪来源混合指标——答案中扎根于文档与工具的比例——在用户抱怨前发现新鲜度问题。

**加分项 / 常见错误：**

- 加分项：每个答案附带机器可读的引用载荷，而不只是可见文本。
- 常见错误：假设模型只使用你给它的上下文。

### 实现

#### 3. 设计 RAG + 记忆 + MCP 数据流。

**答题要点：**

- 在任何检索或工具调用前规范化查询（语言、实体、PII 剥离）。
- 混合检索：BM25 加 embedding，配 reranker，按文档 ACL 和租户限定范围。
- 记忆查找：持久用户事实与知识文档分离；生成时记忆只读，除非维护 Agent 更新。
- 工具层走 MCP：工具注册表带 schema、鉴权、超时和速率限制；只在问题需要实时状态时调用工具。
- 带 provenance 生成，然后验证步骤拒绝无支撑的论断。

**面试官想听什么：**

- Trade-off：实时工具调用权威但慢且贵；缓存文档便宜但过期。要区分"必须调工具"（账单、账户设置）与"检索就够"（文档、how-to）。
- 生产反例：模型从缓存文档回答"你的当前套餐"，而账单 API 早已变化——流畅、带引用、却是错的。
- 数据思维：追踪 recall@k、答案支持度（faithfulness）、引用准确度和新鲜度缺口指标（文档版本时间减查询时间）。

**加分项 / 常见错误：**

- 加分项：弱接地时基于置信度拒绝回答。
- 常见错误：把记忆和知识合并进一个向量库，导致个人事实在用户间泄露。

#### 4. 如何设计多 Agent 通信以避免死锁和决策覆盖？

**答题要点：**

- 使用带 ID 和版本化 schema 的类型化消息；每条消息幂等，重试才安全。
- 每个资源只有一个写入者：退款 Agent 拥有支付状态，工单 Agent 拥有工单状态，其他只读。
- 让决策成为不可变事件：已处理的退款是追加事件，而不是第二个 Agent 可以覆盖的可变字段。
- 检测循环：编排者带跳数上限、每条消息 TTL 和循环检测，防止无限委派。
- 应用超时和熔断：超过预算的工具最多重试 N 次（带退避），然后升级。

**面试官想听什么：**

- Trade-off：编排者集中协调但成为瓶颈和单点故障；点对点分摊负载但让排序和调试变难。
- 生产反例：两个 Agent 都把同一工单视为"未分配"并都尝试退款——没有单写者规则，第二个会覆盖第一个或双重执行。
- 数据思维：统计消息数、重试率、冲突事件和达成共识时间；冲突率随工单量增长说明缺少单写者规则，而不是 prompt 问题。

**加分项 / 常见错误：**

- 加分项：决策事件溯源、确定性胜负裁决（如最小 Agent ID 胜出）、断言精确一次执行的并发测试。
- 常见错误：at-least-once 投递却没有幂等，重试变成重复。

### 调试

#### 5. 调试：Agent 从过期文档而不是实时账单状态回答了"当前套餐"。

**答题要点：**

- 从 trace 复现：回放精确的 prompt、检索块、工具调用和最终答案。
- 生成假设：缓存过期、检索相关性、隐藏工具的 schema 不匹配、缺少新鲜度策略、或偏向文档的 prompt。
- 逐个验证：实时回放工具调用、比较文档时间戳与查询时间、检查接地检查是否运行。
- 从根因修复：让实时状态问题强制调工具（策略，不是 prompt）、给检索块加新鲜度元数据、保持验证开启。
- 添加回归评估用例并针对新鲜度缺口指标告警。

**面试官想听什么：**

- Trade-off：缓存降成本提延迟但牺牲新鲜度；绝不能让 prompt 指令成为模型与过期数据之间的唯一屏障。
- 生产反例：团队在 prompt 里加"套餐问题必须用工具"——在一个评估用例上有效，两周后遇到改写的问法就失败。真正的修复是数据流规则：实时状态问题不能仅靠检索回答。
- 数据思维：增加新鲜度缺口指标和来源混合指标；事故在用户抱怨之前就在这两个指标上可见。

**加分项 / 常见错误：**

- 加分项：在 UI 显示 provenance（"答案来源：doc v3, 2026-08-01"），让用户能看到过期。
- 常见错误：不检查流水线就怪模型——模型只是按上下文允许的方式行事。

#### 6. 上线前如何评估检索 Agent？

**答题要点：**

- 从生产日志构建版本化黄金集：带必需事实的查询、负例、模糊案例和注入尝试。
- 单独度量检索（recall@k、MRR、precision@k），也度量端到端答案质量（支持度、引用准确度、拒绝正确性）。
- 质量之外还要追踪每次查询的延迟与成本。
- CI 门禁：每次 prompt 或检索变更都跑评估，回归阻止合并。

**面试官想听什么：**

- Trade-off：小的人工标注集准确但稀疏；大的自动标注集覆盖广但继承标注噪声。两者都用。
- 生产反例：只用 happy path 构建的评估集，漏掉 Agent 自信回答语料之外内容的失败。
- 数据思维：分别度量误接受与误拒绝；按语言、租户、主题切片，关注长尾而不是均值。

**加分项 / 常见错误：**

- 加分项：黄金集随文档发布版本化，外加红队套件。
- 常见错误：只测检索质量不测答案支持度，无法区分检索 bug 与生成 bug。

### 设计

#### 7. 设计多 Agent 客服系统。

**答题要点：**

- 先澄清意图、权限和边界：哪些动作自主、哪些需确认、哪些总是升级。
- 在网关路由：分类意图与风险，然后分发到专门 Agent（检索、工具执行、升级、记忆），带类型化交接契约。
- 使用置信度阈值与回退：低置信度意图交给通用 Agent 或人工，绝不交给高风险工具。
- 工具执行前强制护栏：工具白名单、参数校验、幂等键、每个动作策略检查。
- 记忆限定范围：当前工单用会话记忆，持久客户记忆仅在用户选择加入且有 PII 边界时使用。
- 记录一切：prompt、检索块、工具调用、决策和评估结果必须可回放。
- 明确预算：路由用小模型，复杂工单才用昂贵推理，稳定检索结果走缓存。

**面试官想听什么：**

- Trade-off：单个通用 Agent 简单便宜，但一个坏 prompt 的爆炸半径大；许多单用途 Agent 增加协调成本和调试负担。要展示折中方案，并用工单量和错误数据证明。
- 生产反例：一个 Agent 持有所有工具（退款、删账号、发邮件），一次误路由就造成伤害；相反失败是 12 个 Agent 的架构，同一客户上下文被取五次、一次失败无法追踪。
- 数据思维：架构前先命名指标——无需人工的解决率、升级率、首次联系解决率、每路由 p95 延迟、每工单成本、护栏误报率——并在开关后对路由器做 A/B。

**加分项 / 常见错误：**

- 加分项：每个变更类工具调用带幂等键；人工交接携带完整 trace。
- 常见错误：没有权限边界——回答问题的 Agent 也能批准退款。

#### 8. 如何消除 Agent 系统中的单点故障？

**答题要点：**

- 列举 SPOF：单一 LLM 供应商、单一 MCP 网关、内存编排状态、单一向量库、同步调用链。
- 有意冗余：第二模型供应商或路由回退；检索只读副本；备用工具网关。
- 持久化编排状态：持久化决策与进行中的步骤，崩溃 worker 恢复而不是重启整段对话。
- 用队列解耦：带重试和 DLQ 的异步处理，慢工具不阻塞整个请求。
- 显式定义降级模式：LLM 宕机时用预置答案加人工队列；工具宕机时明确拒绝并说明，绝不猜测。

**面试官想听什么：**

- Trade-off：双供应商冗余大约翻倍某些可变成本；决策要对应 SLO，而不是恐惧。
- 生产反例："一切依赖编排者"——一个 pod 崩溃丢掉所有活跃会话，因为状态在内存里。
- 数据思维：度量故障转移的 p95 延迟和每个依赖的可用性贡献；把冗余预算花在可用性缺口最大的地方。

**加分项 / 常见错误：**

- 加分项：超时预算和熔断、全链路降级测试、runbook 里的依赖地图。
- 常见错误：计算冗余但状态库单一，故障转移后会话从零开始。

## 追问池

- 如何防止一个 Agent 覆盖另一个 Agent 的决策？
- 如何判断最终答案来自 RAG、记忆还是实时工具状态？
- 什么让多 Agent 系统不安全？
- 检索正确但答案错误时怎么办？
- 你会先故障转移到哪个依赖，为什么？

## 常见红旗

- 数据还没证明单循环是瓶颈就拆分 Agent。
- 把高相关分数当作证明。
- 实时状态问题没有新鲜度策略。
- 共享可变状态没有所有者。
- 变更类工具调用没有幂等键。

## 作品集证据

L3 可接受的证据是：

- 多 Agent 设计文档，含组件边界、错误隔离与成本/延迟预算。
- 评估报告，含版本化黄金集上的 recall@k、答案支持度与拒绝正确性。
- 事故回放，展示根因与防止复发的回归测试。
