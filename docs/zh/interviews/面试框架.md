面试框架

Agent 面试应测量候选人能否构建可靠 Agent 系统，而不是是否背诵框架名。

## 设计原则

- 测 trade-off，不测口号。
- 从 concept 到 implementation、debugging、design。
- 优先具体系统。
- 要求证据：evals、traces、postmortems、follow-up。
- 给假设空间；生产面试考察的是在不完整信息下推理。

## Capability Matrix

| Level | Concept | Implementation | Debugging | Design |
| --- | --- | --- | --- | --- |
| L0 | Prompt、token、context window、model output vs final response | Prompt rewrite | Bad response debugging | Baseline screening |
| L1 | 感知、规划、工具、记忆 | minimal ReAct loop | failed tool loop | single-agent shape |
| L2 | framework fit 与工具边界 | guardrailed single Agent | MCP failure 处理 | tool routing |
| L3 | RAG、记忆、MCP、多 Agent 数据流 | end-to-end pipeline | retrieval misses 与 stale memory | customer support 系统 |
| L4 | evals、observability、safety、rollback | regression suite | incident triage | cost / latency / safety |
| L5 | original patterns 与生态选择 | framework/pattern design | 跨团队失败模式 | ecosystem strategy |

## 题型

### Concept

考察词汇与边界。

示例：

- Agent 的短期记忆和长期记忆有什么区别？

面试官期待听到：

- 短期记忆是对话或任务状态。
- 长期记忆是持久、有作用域、敏感的。
- 记忆可能是错的、过期的或过度提取的。

### Implementation

考察候选人能否把想法变成小系统。

示例：

- 给 ReAct loop 加 max-step 限制和 ambiguous-tool-result 处理。

面试官期待听到：

- Stop condition 防止无限循环。
- 模糊反馈应触发澄清或 fallback plan。
- 系统输出足够状态以便调试失败。

### Debugging

考察运营推理。

示例：

- 用户说 Agent 答错了。你先检查什么？

面试官期待听到：

- 定位 request、trace、prompt、retrieved context、tool calls、final answer。
- 判断失败来自 retrieval、tool execution、model generation 还是 memory。
- 在恢复正常发布流程前补一个 regression eval。

### Design

考察架构判断。

示例：

- 设计一个多 Agent 客服系统。

面试官期待听到：

- 需求分解。
- 组件边界。
- 工具权限。
- 错误隔离。
- 可观测性。
- 成本与延迟预算。

## 系统设计题

作为 L3-L4 的默认系统设计题：

> 设计一个多 Agent 客服系统：能回答产品问题、查询订单状态、更新 support ticket，并把不安全或模糊的案例升级给人工。

推荐结构：

1. 澄清约束：traffic、latency、accuracy、safety、privacy、cost。
2. 定义用户旅程：简单回答、工具动作、ticket 更新、升级。
3. 选择架构：router、检索 Agent、工具 Agent、验证 Agent、升级路径。
4. 定义数据归属：用户会话、策略文档、ticket 系统、审计日志。
5. 定义信任边界：认证、授权、工具 allowlist、不可逆动作确认。
6. 定义可观测性：记录每个规划决策、工具调用、检索来源和最终回答。
7. 定义 evals：正确性、拒答、工具准确率、升级准确率、延迟、成本。
8. 定义回滚：禁用高风险工具路径、回退只读模式、交给人工复核。

## 评分量表

### L0 基础

权重：

- 40% 能解释 prompt、context、token 基础。
- 30% 能从小型 trace 调试错误回答。
- 30% 能区分模型输出与最终用户回答。

### L1 组件理解

权重：

- 40% 清晰定义感知、规划、工具、记忆。
- 30% 能解释最小循环。
- 30% 能识别 stop conditions。

### L2 可靠单 Agent

权重：

- 30% 能解释框架权衡。
- 30% 能设计 guardrails。
- 20% 能处理工具失败。
- 20% 能评估单 Agent 行为。

### L3 端到端系统

权重：

- 25% 检索与记忆边界。
- 25% 多 Agent 分解。
- 20% 错误隔离。
- 20% 可观测性。
- 10% 评估设计。

### L4 生产化

权重：

- 25% 事件响应。
- 25% 根因与预防。
- 20% eval 与回归流程。
- 20% 回滚与成本/延迟控制。
- 10% ownership 与沟通。

### L5 专家

权重：

- 30% 原创模式或框架推理。
- 25% 跨团队失败模式。
- 20% 生态与框架选择。
- 15% 贡献证据。
- 10% 导师或标准制定。

L5 还应考察规范先行起草：提示前用一句话写清目标/接口/验收，并以 [Vibe Coding 工作流](../vibe-coding/README.md) 及 [`vibe_coding_spec` Lab](../../../labs/l5/vibe_coding_spec/README.md) 验证。

## STAR 模板

- Situation：context、constraints、users affected、system boundaries。
- Task：你负责什么、不负责什么、需要哪些决策。
- Action：architecture、tools、evals、safety controls、rollout、rollback。
- Result：metric、incident outcome、learning、follow-up 贡献。

## Portfolio 证据

让候选人把每个 claim 映射到四类项目梯度之一：

1. 个人知识库 Agent：证明 RAG 与记忆。
2. 企业多工具 Agent：证明工具与 MCP 风格编排。
3. 多 Agent 协作系统：证明编排、一致性与失败隔离。
4. 自定义框架或模式：证明抽象、工程深度与贡献准备度。

## Red Flags

- 用框架名替代 reasoning。
- 不提 failure 或 rollback。
- Evals 是可选。
- Safety checks 只在 final prompt。
- Tool calls 默认可信。
- Memory 永远正确。
- Cost 和 latency 只在反复追问后才提及。
