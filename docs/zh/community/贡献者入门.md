# 新人贡献引导

欢迎参与 Agent-Top。这个指南帮助你做出维护者能快速审查的第一次贡献。它不假设你有维护经验，只需要 GitHub 账号和本地 clone。

## 目标

完成本指南后，你应该能够：

- 挑选适合你技能的入门 issue。
- 在本地运行仓库检查。
- 打开一个带正确双语元数据的小 PR。
- 理解审查者检查什么、为什么。

## 开始之前

1. 阅读 [`README.zh-CN.md`](../../../README.zh-CN.md) 和社区索引（[`文档索引.md`](文档索引.md)）。
2. 阅读 [`CONTRIBUTING.zh-CN.md`](../../../CONTRIBUTING.zh-CN.md) 和 [`CODE_OF_CONDUCT.zh-CN.md`](../../../CODE_OF_CONDUCT.zh-CN.md)。
3. Fork 仓库并在本地 clone。
4. 安装 Python 3.10+，并确认 `python` 指向正确解释器。
5. 浏览 [`标签说明.md`](标签说明.md) 理解标签系统。

此设置预计耗时 30-45 分钟。

## 第一步

1. 选一个标签：`good first issue`、`docs-only` 或 `translation-needed`。
2. 在 issue 上评论说你认领，并给出日期。
3. 改动前后都运行本地检查。
4. 保持改动小巧、可审查：一个 issue，一个 PR。
5. 在 PR 里说明改了什么、为什么，并附证据链接。

不要把你的第一个 PR 选成 `maintainer-review` issue。从 `docs-only` 或小翻译开始。

## 标签指南

| 标签 | 适合首个 PR？ | 你会碰什么 |
| --- | --- | --- |
| `good first issue` | 是 | 一个文件或一个小 Lab |
| `docs-only` | 是 | 仅 Markdown，无行为变化 |
| `translation-needed` | 是 | 一个英文页面的中文镜像 |
| `sync-required` | 可能 | 需要同时动 EN/ZH 两个页面 |
| `maintainer-review` | 否 | 架构、安全、生产内容 |

## 本地检查

在仓库根目录打开 PR 前运行：

```bash
python scripts/check_repository.py
python -m unittest discover -s labs -p "test_*.py"
python -m compileall -q labs scripts
python -m ruff check .
```

第一个命令是社区门禁：坏链接、过期 `validated_date`、未配对的双语 key、合并冲突标记都会失败。

## 在这里使用 Vibe Coding

你可以用 AI 助手起草贡献，但验收标准不变：

1. 先写规范：目标、范围、接口、验收。用 [`Vibe Coding 规范模板`](../../../templates/VibeCoding规范模板.md)。
2. 跑任何东西之前审查 diff；拒绝范围蔓延。
3. 运行上面的检查；直到全绿才算完成。
4. 保留证据：在 PR 里粘贴验收命令的输出。

[`Vibe Coding 指南`](../vibe-coding/README.md) 深入讲解了这套工作流，[`vibe coding 规范 Lab`](../../../labs/l5/vibe_coding_spec/README.zh-CN.md) 让"一句话规则"可测试。

## PR 清单

- [ ] 相对链接从当前文件位置解析有效。
- [ ] 内容变化时 `validated_date` 更新到当前日期。
- [ ] Lab 或框架敏感内容带 `tested_against`。
- [ ] 双语文件用同一个 `i18n-key` 配对。
- [ ] 镜像内容变化时更新 `last-synced`。
- [ ] 相关论断链接到可运行示例。
- [ ] 术语与 [`术语表.md`](术语表.md) 一致。
- [ ] PR 标题写明范围，如 `docs: 修复入门文档的坏链接`。

模板 [`../../templates/contribution-checklist.md`](../../../templates/contribution-checklist.md) 就是这份清单；填写并从 PR 链接。

## 写好第一个 PR

- 在 PR 摘要里说明目标与"非目标"。
- 引用或链接你要关闭的 issue。
- 文档改动展示前后对比。
- 翻译指向英文源文件。
- 改了示例就展示命令输出。

## 审查者看重什么

- 清晰范围：一个 issue、一个文件、一个理由。
- 语言准确：术语与术语表一致。
- 可运行示例：测试过的代码，而不是粘贴的。
- 稳定概念与框架 API 分离。
- 不无谓重写可用内容。

## 获取帮助

- 在你的 issue 里用 `@maintainer` 提问。
- 在范围上不确定时先到社区 issue 跟踪器询问，不要猜。
- 被失败检查卡住时，贴出确切的命令和输出。
- 翻译工作先读 [`翻译流程.md`](翻译流程.md)。

## 常见问题与处理

- **坏链接导致检查失败**：从你的文件目录修正相对路径。
- **`i18n-key` 不匹配**：从配对的英文文件逐字复制 key。
- **PR 太大**：拆分；先问审查者保留哪部分。
- **`validated_date` 未更新**：每次内容变更都更新，不只是新文件。
- **审查者要求修改**：3 天内回复；用清单跟踪评论。

## 可衡量指标

社区按季度追踪：

- 从首次评论到首个合并 PR 的时间（目标：少于 14 天）。
- 首个 PR 合并率（目标：高于 80%）。
- 开了第二个 PR 的新贡献者数量（目标：高于 50%）。
- 首个 PR 的平均审查轮数（目标：少于 3 轮）。

## FAQ

- **我需要是 Agent 框架专家吗？** 不需要。大多数首个 PR 是文档或翻译。
- **能同时做两个 issue 吗？** 先做一个；小 PR 更容易审查。
- **issue 已被认领怎么办？** 评论协调；不要打开重复 PR。
- **在哪里找 issue 列表？** 仓库 issue 跟踪器，按 `good first issue` 筛选。
