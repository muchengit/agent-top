# 开源贡献与外部影响力指南

开源影响力是证明 L5 Agent 能力的方式：定义可复用模式、改进工具，并产出别人可以检查的证据。本指南写给想把日常 Agent 工作转化为面向维护者的产物的贡献者：稳定模式、确定性 Lab、评估改进、可观测性契约、文档和工具链。

## 目标读者与目的

- **主要读者**：需要外部可审查的原创模式证据的 L4→L5 学习者，以及审查这些贡献的维护者。
- **目的**：说明高质量贡献包包含什么、如何准备、如何收集外部证据、如何衡量影响力，让审查者可以验证而不是轻信。
- **不适合**：尚未交付过一个可运行单 Agent 的初学者。请先完成 [`学习路径.md`](../tutorials/学习路径.md)。

## 贡献类型

- **Pattern contribution**：提交稳定 Agent pattern 与测试或例子。
- **Lab contribution**：增加确定性练习来解释设计 trade-off。
- **Evaluation contribution**：改进 eval design、negative cases 或 release gates。
- **Observability contribution**：增加 trace contract、alert 例子或 debugging workflow。
- **Documentation contribution**：澄清概念、mapping、glossary 或 contributor paths。
- **Tooling contribution**：改进 CI、docs checks、templates 或本地校验。

## 好的贡献包

贡献应包含：

- Problem statement。
- 稳定 pattern 或 workflow。
- 最小可复现例子。
- Tests 或 validation commands。
- Failure modes。
- Maintainer notes。
- 双语文档。
- 关联 concepts 和 Labs。

## 分步骤工作流

1. **选定一个缺口**。开始前先搜索 issues、贡献路径和模式矩阵。
2. **写 problem statement**。用一段话说明用户、任务和你观察到的失败。
3. **本地原型**。使用最小可复现例子，并记录能复现行为的命令。
4. **稳定模式**。把稳定想法与框架胶水代码分开，并记录最先会坏的部分。
5. **添加确定性证据**。添加 tests、eval cases 或 Lab，让结论可以重新运行。
6. **开一个小 PR**。保持 diff 可审查，运行 repository checks，写审查者友好的描述。
7. **收集外部证据**。链接被接受的 PR、维护者评论和任何后续使用。

## 如何选择第一个贡献

- **从你失败过的地方开始**。最有说服力的贡献来自你自己项目中踩过的 bug 或 trade-off。
- **优先 Lab 而不是文章**。确定性练习比散文更能教会一个 trade-off。
- **遵循仓库惯例**。写新 Lab 前先读贡献路径和现有 Labs。
- **第一个 PR 保持小**。一个模式、一个 Lab 或一个 eval 改进足够起步。
- **询问缺口清单**。维护者 issues 常把 [`good-first-L5`](../../../docs/en/community/labels.md) 候选标记为外部影响力。

## 提 PR 前检查

- 运行 repository checks。
- 确认 pattern 不只是 framework API wrapper。
- 把稳定概念和框架代码分开。
- 加入 negative examples 或 non-usage cases。
- 解释 pattern 失败时怎么办。
- AI 辅助起草时，先用 [Vibe Coding 工作流](../vibe-coding/README.md) 写一句话规范（目标、接口、验收）。

## 外部证据

可用的外部证据：

- 被接受的 PR。
- Maintainer 对 trade-off 的评论。
- Talk 或 workshop notes。
- 带例子的 pattern 文章。
- 被学习者使用的 Lab。
- 显示 adoption 或 follow-up use 的 issue thread。

## Impact 陈述模板

```markdown
# Contribution Impact

## Problem
这次贡献解决什么缺口？

## Pattern
引入什么可复用想法？

## Evidence
哪些测试、例子或 review 证明它有效？

## Adoption
下一批用户是谁？

## Follow-Up
还有什么没覆盖？
```

## PR 描述示例

```markdown
## Problem
工具结果在无出处的情况下被接受，导致陈旧数据悄悄传播。

## Pattern
provenance-check gate：每个工具结果在 planner 看到之前都带上
source、timestamp 和 fetch status 标签。

## Evidence
- 2 个 negative eval cases，在 gate 之前失败、在 gate 之后通过。
- 1 个可用 `python ../../../labs/l3/rag_evaluator` 运行的确定性 Lab。
- 用 `python scripts/check_repository.py` 通过 repository checks。

## Notes for Reviewer
需要检查的失败模式：provenance 来源本身不可用时会发生什么。
该模式保持 planner 不变，只守卫数据层。
```

## 常见错误与规避

- **跳过 problem statement**——审查者无法评估意图。始终从缺口开始。
- **包装 framework API**——薄封装不是原创模式。展示你阻止的设计决策和失败模式。
- **混用稳定代码与版本特定代码**——把框架相关部分放进独立层，让模式能扛过升级。
- **只有正面例子**——加入 negative cases 或 non-usage cases，让模式的边界可见。
- **静默失败**——描述模式失败时会发生什么、如何检测。
- **忽略 repository checks**——开 PR 前运行 `python scripts/check_repository.py`。

## 可衡量指标

- **Adoption**：引用该贡献的 issue threads、下游 Labs 或学习者使用。
- **Reviewability**：带维护者 trade-off 评论的被接受 PR。
- **Reproducibility**：审查者能一次性重跑测试或 validation commands。
- **Reach**：解释该模式的 talk notes、workshop notes 或文章。
- **Retention**：模式扛过仓库升级，或新贡献者接手使用它。

## 维护者视角

- **维护者验证，不轻信。**PR 描述里的每个论断都需要可重跑的测试或 Lab。
- **Negative cases 是判断力的证明。**它们说明你知道模式在哪里失效。
- **小 diff 获得审查。**把大贡献拆成一串 PR。
- **双语同步是完成的定义之一。**zh 镜像必须保持相同的 `i18n-key` 和 `last-synced` 日期。

## 真实示例片段

```markdown
# Contribution Impact

## Problem
单 Agent 部署在没有出处的情况下接受工具结果，陈旧数据悄悄传播。
用户要求的重试掩盖了真正的失败。

## Pattern
provenance-check gate：每个工具结果在 planner 看到之前都带上
source、timestamp 和 fetch status 标签。

## Evidence
- 2 个 negative eval cases，在 gate 之前失败、在 gate 之后通过。
- 1 个可用 `python ../../../labs/l3/rag_evaluator` 运行的确定性 Lab。
- 维护者评论："failure-mode section 让 trade-off 很清晰。"

## Adoption
任何合并多来源结果的 RAG 或 MCP 型 Agent。

## Follow-Up
provenance 来源本身不可用时怎么办。
```
