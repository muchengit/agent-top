# 规范先行工作流

## 原则

提示质量是规范质量的直接函数。先写规范，再写提示。

## 一份好的规范包含

- **目标**：变更后应该成立的事实。
- **范围**：涉及和不涉及的文件或组件。
- **接口**：输入、输出和错误行为。
- **验收**：必须通过的精确检查。
- **约束**：变更绝不能破坏什么。

## 示例

模糊提示：

> "加一个搜索端点。"

清晰提示：

> "给现有 FastAPI 应用新增 `GET /search?q=...` 端点。它查询向量库，最多返回 10 条 `{id, score, source}`，空查询返回 `400`。验收：`pytest tests/api/test_search.py` 通过，且 trace 包含检索来源。"

## 工作流步骤

1. **一句话**：用一句话复述目标。说不清就先调研。
2. **写规范**：即使是一个文件的小改动，也填满上面五个字段。
3. **提示 diff**：要求具体补丁，而不是讨论。
4. **审查 diff**：核对范围是否符合规范，拒绝无关变更。
5. **运行验收检查**：使用评审者会跑的同一命令。
6. **用证据打磨**：失败时贴出真实错误和失败输入，而不是"它不工作"。
7. **绿灯且小改动时停止**：检查通过后，忍住"再加一个小东西"的冲动。

## 什么时候可以跳过规范

- 一行错别字修复，diff 不言自明。
- 机械式重命名，且编译器和 formatter 能确认。

## 什么时候规范不是正确的工具

- 开放式调研（"看看有哪些模式"）——在变更循环之外做。
- 没有客观检查的架构决策——写设计说明，而不是提示。
