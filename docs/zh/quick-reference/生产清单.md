# 生产清单

这份清单用于发布前、事故中和 postmortem 后。它是详细生产指南之上的快速查找层；每个小节都指向解释"为什么"的支撑文档。

## 目的与适用范围

本页是发布和运营 Agent 系统的操作门禁。它适用于发布、事故响应和后续行动。前提是已经读过生产指南；在真实发布或事故期间把它当作可执行摘要使用。

支撑指南：

- [`../production/评估清单.md`](../production/评估清单.md)：发布门禁评估。
- [`../production/可观测性与Trace契约.md`](../production/可观测性与Trace契约.md)：必需 trace 字段。
- [`../production/安全清单.md`](../production/安全清单.md)：auth、工具和记忆控制。
- [`../production/季度维护.md`](../production/季度维护.md)：新鲜度与废弃管理。
- [`../production/成本稳定性运行手册.md`](../production/成本稳定性运行手册.md)：预算与护栏。

## 发布前

- [ ] Auth 和 permissions 已定义。
- [ ] Tool allowlist 和风险分类存在。
- [ ] Destructive actions 需要确认。
- [ ] Safety evals 通过。
- [ ] Golden prompts 通过。
- [ ] Trace fields 存在。
- [ ] Rollback plan 已记录。
- [ ] Cost 和 latency budgets 已设置。
- [ ] Incident owner 已命名。
- [ ] PII handling 和 data retention 已记录。
- [ ] Rate limits 和 retry budgets 已定义。
- [ ] Model/provider fallback 已测试。
- [ ] Regression gate 阻断 safety 和 eval failures。
- [ ] Human escalation path 已记录。

## 事故中

- [ ] 禁用 risky action path。
- [ ] 必要时 freeze writes。
- [ ] 检查 traces。
- [ ] 定位 root cause。
- [ ] 添加 regression eval。
- [ ] 记录 postmortem。
- [ ] 通知 stakeholder 并说明 blast radius。
- [ ] 从 traces 和 logs 保留 before/after evidence。
- [ ] 确认 rollback 或 mitigation 有效。

## 事故后

- [ ] Fix owner 和 due date 已指派。
- [ ] Rollback 已测试。
- [ ] Evals 已更新。
- [ ] 文档已更新。
- [ ] Follow-up 被监控。
- [ ] 已添加预防性 guardrail。
- [ ] Action items 已链接到 postmortem。

## 运行门禁

发布前运行确定性回归门禁与仓库检查：

```bash
python -m unittest labs.l4.regression_gate.test_lab
python scripts/check_repository.py
```

预期输出：测试以 `OK` 结束，脚本打印 `Repository checks passed`。

## 严重级别与响应时间

| 级别 | 示例 | 响应目标 | 第一步动作 |
| --- | --- | --- | --- |
| S0 | 数据丢失、不安全的工具执行 | 15 分钟 | 禁用风险路径，冻结写入 |
| S1 | 大规模错误回答、成本失控 | 60 分钟 | 检查 traces，定位 root cause |
| S2 | 局部错误行为 | 下一个工作日 | 添加 regression eval |
| S3 | 外观或文档问题 | 下一次季度审查 | 记录 issue 并指定 owner |

## 角色与责任

| 角色 | 发布 | 事故 |
| --- | --- | --- |
| 发布经理 | 运行门禁、签署发布 | 协调缓解与回滚 |
| 事故响应人 | — | 负责时间线与 root cause |
| 评估 owner | 运行并记录评估 | 添加回归用例 |
| On-call 工程师 | 验证预算与 fallback | 执行 runbook |
| 安全评审 | 批准破坏性动作策略 | 在 traces 中验证护栏判定 |

## 常见失败与处理

| 失败 | 症状 | 处理 |
| --- | --- | --- |
| 门禁处 safety eval 失败 | `regression_gate` 测试失败 | 阻断发布，修复护栏，重跑套件 |
| 缺失 trace 字段 | postmortem 无法复现 | 在契约中补上字段并重新部署 |
| 成本失控 | prompt 变更后账单飙升 | 启用成本护栏，回滚 prompt，添加预算告警 |
| fallback 未测试 | 供应商故障导致 Agent 宕机 | 在发布前门禁中添加 fallback 测试 |
| 逃生路径缺失 | 找不到事故 owner | 发布前指定 owner 并记录路径 |

## 发布后跟进

发布后一个工作日内确认：

- [ ] 发布说明与版本锚点已更新（`validated_date`、`tested_against`）。
- [ ] 已审查 canary 窗口的 traces，确认必需字段。
- [ ] 预算使用与计划对比；任何超支都有 owner。
- [ ] 在发布的实际模型/prompt 版本上重跑 evals。
- [ ] 回滚触发条件已记录给 on-call 工程师。
- [ ] 已向 stakeholder 发送更新，包含实测 blast radius 与缓解状态。

## 金丝雀与回滚决策矩阵

| 条件 | 决策 |
| --- | --- |
| 所有阻断评估通过、traces 完整、预算在范围内 | 全量发布 |
| 仅非阻断评估失败、风险有界 | 10% canary，24 小时后重新评估 |
| Safety eval 失败或缺失 trace 字段 | 阻断，不发布 |
| Latency/cost 超阈值 | 回滚到上一 prompt/model 版本 |
| 工具行为变化影响破坏性动作 | 回滚并重跑 tool usage evals |
| Fallback 路径已被验证 | 继续发布并记录验证结果 |

## 关键指标

| 指标 | 检查点 | 告警级别 |
| --- | --- | --- |
| Safety eval 通过率 | 发布门禁 | 必须 100% |
| Golden 通过率 | 发布门禁 | 无回归 |
| Trace 完整性 | canary 窗口 | 100% |
| p95 延迟 | 发布门禁 + canary | 预算内 |
| 每任务成本 | 发布门禁 + canary | 预算内 |
| 回滚时间 | 季度演练 | ≤ 15 分钟 |
| 错误率 | canary 窗口 | 超过基线 2 倍 |

## 审批与升级路径

- [ ] On-call 工程师持有回滚触发权与已记录的 runbook。
- [ ] 破坏性动作审批使用指定审批人，而不是 Agent 自己。
- [ ] 预算超支需书面例外，含到期时间与监控计划。
- [ ] S0 事故在 15 分钟内升级到发布经理与安全评审。
- [ ] 每个例外都链接到 postmortem 或带日期的风险决策。

## 验证命令

运行以下命令并把输出记录到发布工单：

```bash

# 2. 成本与稳定性护栏

# 3. 大变更时运行完整 Lab 套件

# 4. 仓库检查（链接、frontmatter、双语配对）
python scripts/check_repository.py
```

## 完成定义

满足以下全部条件才视为发布完成：

- [ ] 在实际发布的模型/prompt 版本上通过发布门禁。
- [ ] 已用 canary 窗口验证 trace schema。
- [ ] 预算报告由发布经理签署。
- [ ] 上次季度演练已演练回滚计划。
- [ ] 已记录事故 owner、升级路径与 stakeholder 列表。
- [ ] Evals 与清单已更新，文档链接是最新的。
- [ ] 发布后回顾中无未解决的 S0/S1 事项。
